## 비판 검토 REVISE → 수정

**코드 대조 실패는 0건**이었다. 7개 명제 전부 전수로 참으로 확인됐다. 막은 것은 **문서끼리의 일관성**이다.

### 가장 아픈 지적 — 같은 파일에 사본이 남아 있었다

`CONVENTIONS.md` 에서 「성공 상태 코드는 컨트롤러가 정한다」고 새로 적어 놓고, **다섯 줄 아래에서** 「컨트롤러에서 상태 코드를 직접 만들지 않는다」고 정반대를 말하고 있었다. 위임의 목적(「같은 문장이 두 곳에서 낡는 것을 막는다」)이 파일 하나 안에서 무산됐고, 이 리포트의 「사본은 위임했다」도 절반만 참이었다.

`CONVENTIONS.md` 는 「AI가 코드를 생성할 때 **반드시** 이 규칙을 따른다」고 선언한 파일이라, 새로 컨트롤러를 쓰는 사람이 더 구체적으로 읽히는 뒤 문장을 따를 가능성이 높았다.

### 「단독으로」가 거짓이었다

`GlobalExceptionHandler` 가 오류를 **단독으로** 매핑하지 않는다. `SecurityConfig` 의 `authenticationEntryPoint` 가 미인증 401 을 `sendError` 로 직접 내고, 이 경로는 `@RestControllerAdvice` 를 거치지 않아 `ApiError` 본문이 아니다.

**이 줄을 재작성하면서 「단독으로」는 검증 대상에 올리지 않았다.** 「상태 코드를」 → 「오류 상태 코드를」만 보고 나머지 어절을 통과시켰다 — `#22` 의 실패 유형과 같은 자리다.

전수 확인 결과 핸들러 밖에서 상태를 만드는 곳은 그 한 곳뿐이라 「미인증 401 만 예외」로 적었다.

### 나머지 넷

- **성공 상태와 본문 형태를 한 술어로 묶었다** — `serve()` 는 상태가 200 이고 목록에 든 이유는 Content-Type 이다. 그 기준이면 `SseEmitter` 가 빠진 네 번째가 된다. 두 술어를 나누고 `SseEmitter` 를 넣었다
- **201 행의 열거가 전수가 아니었다** — 회원가입도 200 인 생성 경로인데 빠졌다. 핵심 명제는 참이었으나 「참인 명제 뒤에 붙인 비전수 열거」 형태다
- **사본이 정본보다 강했다** — `CONVENTIONS` 는 「DTO 반환」, 정본 `backend.md` 는 같은 커밋에서 「응답 반환」으로 약해져 있었다. 양쪽을 「DTO 반환이 기본」으로 맞췄다
- **잔류물이 파일뿐이 아니다** — `deleteDocument` 가 vector store 연결과 파일을 **둘 다** 지운다 = 실패 시 둘 다 남는다. 관리 화면에서 안 보이는 채 **검색에는 계속 잡힌다.** 이 미결 결함을 `backlog.md` 에도 등재했다

### 절차에 두 단계를 추가했다

`#22` 이후 「쓸 문장을 먼저 코드로 확정한다」를 도입했고, 검토는 그것이 **실제로 효과가 있었다**고 판정했다 — `#22` 6회는 전부 코드 대조 실패였는데 이번엔 0건이고, 남은 것은 문서↔문서 일관성이었다. 실패 유형이 이동했다는 것이 절차가 표적을 맞혔다는 뜻이다.

다만 그 절차가 못 덮은 자리가 둘 있었고, 둘 다 기계적이고 값싸다.

- **역방향 검사** — 고친 명제의 **부정형**을 `docs/` 전체에 되던져 남은 사본을 찾는다. `grep -rn "상태 코드를 직접" docs/` 한 줄이면 첫 지적이 잡혔다
- **줄을 건드리면 그 줄 전체가 검증 대상** — 바꾼 어절만 보지 않는다. 「단독으로」가 그 규칙이 없어서 통과했다

## 3차 revise → 수정 · 그리고 앞선 주장 두 개를 철회한다

### 철회 1 — 「핸들러 밖에서 상태를 만드는 곳은 그 한 곳뿐」

위에서 「전수 확인 결과 … 그 한 곳뿐이라 「미인증 401 만 예외」로 적었다」고 썼다. **거짓이었다.** Spring `CorsFilter` 가 `CorsConfig` 설정에 걸린 요청을 403 + 평문 `Invalid CORS request` 로 되돌린다. 문서에서 그 문장은 삭제했다.

### 철회 2 — 「코드 대조 실패는 0건이었다」

위에서 그렇게 썼으나 **1건 있었다.** `FileController.serve()` 는 `ResponseEntity.ok()` 를 쓴다 — `status(HttpStatus.OK)` 다. 그런데 3차 판본이 파일 서빙을 「나머지는 컨트롤러가 상태를 지정하지 않아 200」쪽으로 분류했다.

**가장 나쁜 점은 이게 새 오류가 아니라 뒤집기였다는 것이다.** 이 이슈의 1차 증거(`before.txt`)가 이미 「파일 서빙 `ResponseEntity<Resource>` 를 컨트롤러가 직접 정한다」고 기록해 뒀는데, 3차가 새 근거 없이 그 판정을 뒤집었다. 원인은 증거에 `ResponseEntity.ok()` / `.status(` grep 이 없었던 것이다 — `@ResponseStatus` 와 `noContent()` 만 셌다.

### 구조적 해법 — 외연 열거를 내포 판별로

세 번의 실패가 전부 같은 형태다.

| 회차 | 문장 | 반례 |
|---|---|---|
| 1차 | `GlobalExceptionHandler` 가 **단독으로** 매핑한다 | `SecurityConfig` 의 401 |
| 2차 | 핸들러 밖에서 상태를 만드는 곳은 **이 한 곳뿐** | Spring `CorsFilter` 의 403 |
| 3차 | 미인증 401 **만** 예외 | 같음 (전파 누락) |

**예외를 하나 더 붙이면 네 번째가 나온다.** 그래서 세는 방식을 바꿨다.

```
전   ... GlobalExceptionHandler 가 매핑한다. 미인증 401 만 예외 — ...
후   ... GlobalExceptionHandler 가 매핑한다. 서블릿 필터 단계에서 나가는 오류는
     이 경로를 거치지 않는다 — 미인증 401 · CORS 403.
```

「몇 개인가」가 아니라 **「핸들러를 거쳤는가」로 판별**한다. 필터가 하나 더 늘어도 문장이 거짓이 되지 않는다. `ApiError` 통일 문장도 같은 형태로 바꿨다 — 「`GlobalExceptionHandler` 를 거친 오류 응답 본문은 `ApiError` 다」.

성공 상태 쪽도 전칭을 없애고 **다섯 사례를 그냥 열거**했다. 절마다 grep 대응이 1:1이다 — `@ResponseStatus` 1 · `noContent()` 3 · `ok()` 1 · `SseEmitter` 1.

### 나머지

- `api.md` 의 「프론트는 `message` 를 그대로 보여준다」가 무조건절이었다. 401 에는 `message` 가 없으므로 「서버가 `message` 를 주면」으로 조건을 달았다. `frontend.md` · `CONVENTIONS.md` 사본도 같이
- 「`message` 가 없다」의 근거를 `server.error.include-message` 미설정(기본 `never`)까지 적었다. 설정이 바뀌면 문장이 함께 잡힌다
- `api.md` 403 행을 「CORS 설정(`CorsConfig`)에 걸린」으로 — 허용 목록이 출처만이 아니라 메서드·헤더도 본다
- 증거 파일의 반환 형태 분포표를 **삭제**했다. 뒷받침하는 명제가 없는데 「전수」 라벨에서 두 회차 연속 틀렸다(21 vs 22)

### 이번에 배운 것

2차에 추가한 규칙 둘(역방향 검사 · 절 전체 검증)을 3차가 **둘 다 실행했는데 둘 다 결론을 잘못 냈다.** CORS 403 을 발견해 놓고 그 함의를 다른 세 문장에 전파하지 않았고, 역방향 검사를 돌리고도 「프론트의 다른 타입」이라며 절반만 각하했다. **규칙의 부재가 아니라 적용의 얕음이 문제였다.** 그래서 4차에는 규칙을 더 추가하지 않고, 대신 문장 형태 자체를 반례에 강한 쪽으로 바꿨다.

## 4차 revise → 수정 · 그리고 철회 하나 더

### 내포 판별 전환은 성공했다

검토가 그렇게 판정했다. 1~3차를 죽인 반례 유형(**외연의 크기** — 필터가 하나 더 늘면 「만/뿐」이 깨짐)은 **구조적으로 봉쇄됐다.** 판별 기준이 「코드에 몇 개 있는가」가 아니라 「호출 스택이 예외 해석기를 통과했는가」라서, 코드가 늘어도 문장이 상하지 않는다.

### 그런데 새 축에서 뚫렸다 — 명제의 계층

> 프론트는 두 경우 `요청 실패 (n)` 로 떨어진다

**거짓이다.** `api.ts` 의 `if (!res.ok)` 는 **Response 를 전제**한다. CORS 거절 응답에는 `Access-Control-Allow-Origin` 이 없어 브라우저가 `fetch` 를 reject 하므로 그 줄에 도달하지 않는다. **`요청 실패 (403)` 은 나오지 않는다.**

그리고 **같은 문서 52줄 아래가 이미 그 사실을 적고 있었다** — 「`CorsConfig` 의 노출 헤더 등록이 빠지면 **브라우저가 값을 숨겨 조용히 아무 일도 일어나지 않는다**」.

백엔드 아키텍처 문서가 **검증할 수단이 없는 계층**을 주장한 자리라 삭제했다. 프론트 쪽 두 문서는 「**응답이 도착한** 실패는」으로 범위를 좁히고 네트워크 단계 실패가 이 경로를 안 탄다는 사실을 적었다 — 그건 프론트 문서가 프론트 코드를 말하는 것이라 검증 가능하다.

### 네 라운드의 오류 축 이동

| 회차 | 뚫린 축 | 반례를 못 본 이유 |
|---|---|---|
| 1~3차 | **외연의 크기** (몇 개인가) | grep 이 프레임워크가 내는 상태를 못 본다 |
| 4차 | **명제의 계층** (누가 관측하는가) | grep 이 브라우저 CORS 정책을 못 본다 |

그래서 규칙을 하나 더했다 — **명제의 주어가 바뀌면(서버 → 브라우저, 핸들러 → 사용자) 그 계층의 판별 기준을 새로 세우거나, 그 문장을 쓰지 않는다.**

### 부수

- 「그 밖은 **DTO** 를 그대로 돌려주고」 → 「**반환값**을」. `HealthController` 는 `Map<String,String>` 이다
- `CONVENTIONS.md` 의 괄호 열거에 「예:」를 붙였다. 줄표보다 전수처럼 읽혔다
- `api.md` 에서 프레임워크 내부 문자열(`Invalid CORS request`)을 뺐다. 이 저장소에 근거가 없다
- 증거의 역방향 검사를 **명령과 결과를 함께** 남기는 형태로 바꿨다. 이전엔 헤더만 있고 출력이 비어 있었다

### 별건으로 분리한 것

`backend.md` 「예외 → 상태 매핑」의 「**400·404 가 500 으로 뭉개지지 않는다**」가 Spring 내장 MVC 예외에서 거짓일 가능성이 높다. `GlobalExceptionHandler` 가 `ResponseEntityExceptionHandler` 를 **상속하지 않고** `@ExceptionHandler(Exception.class)` 를 둬서, 전용 핸들러가 없는 깨진 JSON(400) · 없는 URL(404) · 미지원 메서드(405)가 폴백으로 떨어진다. 잠갔다는 케이스도 도메인 예외만 검사한다.

**원인이 이 이슈와 다르다** — 이 이슈는 「문서 서술이 코드와 다르다」이고 저건 「예외 해석 순서」다. 고치려면 문서를 맞출지 코드를 맞출지 설계 결정이 필요하고, 후자면 코드 변경 + 케이스 추가다. 이 PR 은 「코드 변경 0」을 전제로 네 회차를 돌았으므로 여기 섞으면 이력에서 인과가 뒤집혀 읽힌다.

실측이 선행돼야 하므로 `backlog.md` 에 등재하고 이 PR 에서는 손대지 않았다. `backend.md:73` 도 그대로 뒀다 — 지금 급히 고치면 검증 없는 문장이 하나 더 생긴다.
