## 2) 보장의 근거 — 비둘기집 원리 (샘플이 아니라 증명이다)

  **한 번 통과한 것으로는 간헐 실패를 고쳤다는 증명이 안 된다.** 그래서 경우를 전수로 따진다.

  전제 : 세 요청은 밀리초 안에 끝나므로 분 경계는 **최대 한 번** 끼어든다. 즉 창은 최대 2개다.
  상한 1 이므로 `increment(key) > 1` 에서 **한 창이 2개 이상 받으면 반드시 거절이 나온다.**

  비둘기집 : 요청 3개를 창 2개에 넣으면 **어느 창은 ceil(3/2) = 2 개 이상**을 받는다.
  따라서 거절이 **반드시 1건 이상** 생긴다. 전수로 확인하면 :

    (3,0) -> max(0,3-1) + max(0,0-1) = 2 + 0 = 2
    (2,1) -> max(0,2-1) + max(0,1-1) = 1 + 0 = 1
    (1,2) -> max(0,1-1) + max(0,2-1) = 0 + 1 = 1
    (0,3) -> max(0,0-1) + max(0,3-1) = 0 + 2 = 2

  최소 1. **확률이 아니라 하한이다.**

  ### 이 증명이 기대는 전제 — 숨기지 않고 적는다

  **「창이 2개 이하」가 전제다.** 요청 3개가 창 **3개**에 하나씩 쪼개지면 어느 창도 상한을 넘지
  못해 다시 거절 0건이 된다. 창이 3개가 되려면 세 요청이 **1분을 걸쳐야** 한다.

  실측 (surefire, 2026-09-12 · 4회 시행 · 세 요청 + 계정 생성 포함) :

    upload_over_the_limit_is_rejected            0.285 ~ 0.301s
    upload_limit_is_per_user                     0.569 ~ 0.636s
    password_change_over_the_limit_is_rejected   0.412 ~ 1.724s   <- 가장 느리다 (BCrypt)

  **최악값 1.724초 대 60초 = 약 35배 여유.**

  **처음에는 100배라고 적었다가 고쳤다.** 첫 시행에서 password_change 가 0.412초로 나온 것만 보고
  적었는데, 이어진 세 시행에서 1.724 / 1.632 / 1.428초가 나왔다. **0.412초가 이상치였고 그것을
  골라 쓴 셈이다.** 반복 실행이 아니었으면 그대로 넘어갔을 값이라 남긴다 —
  **여유를 말할 때는 가장 빠른 시행이 아니라 가장 느린 시행을 쓴다.** 그래도 전제는 전제이므로 테스트 주석에 적어 두었다 —
  요청 사이에 sleep 을 넣거나 BCrypt 강도를 크게 올리는 변경을 하면 이 여유가 줄어든다.
  창 W 개를 견디려면 요청이 W 개보다 많아야 한다(상한 1 기준).

  요청을 4개로 늘리면 창 3개까지 견디지만(여유 120초), 지배적인 안전 계수는 이미 위 100배이고
  비밀번호 변경은 요청당 BCrypt 가 두 번 돌아 **늘리는 비용이 얻는 것보다 크다**고 판단했다.

  (before 는 상한 2 · 요청 3번이라 (2,1) 과 (1,2) 에서 거절이 0건이었다 — before 증거의 3절 참고)

  그리고 **첫 요청은 어느 창에서든 그 창의 첫 번째**이므로 `1 > 1` 이 아니라 항상 통과한다.
  「상한 안의 요청은 통과해야 한다」(이 파일 주석)가 지켜진다.

## 3) 단언을 두 방향으로 유지했다

  104: 	void upload_over_the_limit_is_rejected() {
  105: 		String token = createUser("upload-limit@b.com");
  106: 
  107: 		var codes = repeat(3, () -> upload(token));
  108: 
  109: 		assertThat(codes.get(0))
  110: 				.withFailMessage("첫 업로드가 막힘 - 상한 안의 요청까지 거절하는 구현이다 (관측: %s)", codes)
  111: 				.isEqualTo(HttpStatus.OK);
  112: 		assertThat(codes)
  113: 				.withFailMessage("세 번 중 429 가 한 번도 없음 - 업로드에 유량 상한이 없다는 뜻 (관측: %s)", codes)
  114: 				.contains(HttpStatus.TOO_MANY_REQUESTS);
  115: 	}
  116: 

  「어딘가에서 429」만 보면 무조건 거절하는 구현이 통과하고,
  「정확히 3번째가 429」를 보면 종전 결함으로 돌아간다. 둘을 함께 본다.
  실패 메시지에 관측된 코드 목록(`%s`)을 찍어 다음 사람이 바로 알게 했다.
