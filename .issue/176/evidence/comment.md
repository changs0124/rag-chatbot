## 작업 요약

`UploadRateLimitTest` 세 건을 **고정 윈도우 경계에 흔들리지 않게** 고쳤다.
상한을 2 → 1 로 낮추고 **요청 횟수는 3번 그대로** 두었다.

## 무엇이 문제였나

| | before | after |
| --- | ---: | ---: |
| 테스트 상한 | 2 | **1** |
| 보내는 횟수 | 3 (상한+1) | 3 (상한×2 초과) |
| 경계가 끼었을 때 거절 하한 | **0건** | **1건** |

고정 윈도우라 분이 바뀌면 카운터가 0 으로 새로 시작한다(`RateLimiterService.java:114-123`).
상한 2 · 요청 3번에서는 두 창에 `(2,1)` 또는 `(1,2)` 로 쪼개지면 **어느 창도 상한을 넘지 못해**
거절이 한 건도 안 나왔다. `CONVENTIONS.md:104` 가 **「상한의 두 배 넘게 보내라」**고 적어 둔 함정이다.

## 왜 이슈의 1안을 그대로 쓰지 않았나

이슈는 「상한 2 유지 + 요청 5번」을 먼저 제시했다. 같은 효과지만 **비밀번호 변경은 호출당
BCrypt 가 두 번 돈다**(현재 비밀번호 검증 + 새 해시). 요청을 5번으로 늘리면 BCrypt 가 10번 돌아
테스트가 느려진다. **상한을 1로 낮추면 요청 3번 그대로**이고 BCrypt 횟수도 그대로다.

## 보장의 근거 — 샘플이 아니라 증명이다

**한 번 통과한 것으로는 간헐 실패를 고쳤다는 증명이 안 된다.** 그래서 경우를 전수로 따졌다.

세 요청은 밀리초 안에 끝나므로 분 경계는 **최대 한 번** 끼어든다 — 창은 최대 2개다.
**비둘기집 원리** : 요청 3개를 창 2개에 넣으면 어느 창은 `⌈3/2⌉ = 2` 개 이상을 받고,
상한 1 에서는 그 창의 2개째가 **반드시 거절된다.**

```text
(3,0) -> max(0,3-1) + max(0,0-1) = 2
(2,1) -> max(0,2-1) + max(0,1-1) = 1
(1,2) -> max(0,1-1) + max(0,2-1) = 1
(0,3) -> max(0,0-1) + max(0,3-1) = 2
```

**최소 1. 확률이 아니라 하한이다.**
그리고 첫 요청은 어느 창에서든 그 창의 첫 번째라 `1 > 1` 이 아니므로 **항상 통과**한다.

## 단언을 두 방향으로 유지했다

이 파일이 이미 적어 둔 것을 지켜야 한다 — *"상한 안의 요청은 통과해야 한다. 그것까지 막히면
「무조건 거절하는 구현」이 통과한다."*

```java
var codes = repeat(3, () -> upload(token));

assertThat(codes.get(0))   // 첫 요청은 통과
        .withFailMessage("첫 업로드가 막힘 - 상한 안의 요청까지 거절하는 구현이다 (관측: %s)", codes)
        .isEqualTo(HttpStatus.OK);
assertThat(codes)          // 어딘가에서 429
        .withFailMessage("세 번 중 429 가 한 번도 없음 - 업로드에 유량 상한이 없다는 뜻 (관측: %s)", codes)
        .contains(HttpStatus.TOO_MANY_REQUESTS);
```

「어딘가에서 429」만 보면 무조건 거절하는 구현이 통과하고, 종전처럼 **「정확히 3번째가 429」**
를 보면 경계에 다시 흔들린다. **몇 번째가 429 인지는 단언하지 않는다** — 경계 때문에 정해지지 않는다.
실패 메시지에 관측된 코드 목록을 찍어 다음 사람이 바로 알게 했다.

## 머리주석도 고쳤다

종전 주석은 「상한을 낮게 두어 결정적으로 만든다」로 **동시 요청 타이밍**만 다뤘다.
그 판단 자체는 옳지만, 그것과 **고정 윈도우 경계**는 서로 다른 실패 원인이고 상한을 낮추는 것으로
경계가 사라지지 않는다. **그 구분이 없던 것이 이 결함이 오래 남은 이유로 보인다** — 두 원인을
나눠 적었다.
