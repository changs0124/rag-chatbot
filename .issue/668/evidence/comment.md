## #668 모바일 키보드 열고 닫힘 반응 — 전후 측정

### 원인(코드 확인)

`ChatPage` 가 `visualViewport` 의 `resize` · `scroll` 이벤트마다 `setViewportHeight` 로 React 상태를 바꾸고 `window.scrollTo(0,0)` 를 불렀다(#221). iOS 는 키보드 애니메이션 동안 이 이벤트를 프레임마다 보내 채팅 화면 전체가 프레임마다 다시 그려졌다.

### 수정

높이를 상태가 아니라 루트 요소(`rootRef`)에 바로 쓴다. 한 프레임에 한 번(`requestAnimationFrame`), 같은 높이면 건너뛰고, 문서가 실제로 밀렸을 때만 `scrollTo`. #221 의 두 장치(루트 높이 = 보이는 영역, 확대 중 무시)와 문서 스크롤 · 튕김 잠금은 그대로.

### 측정 (`k668.mjs` — 가짜 visualViewport 로 높이 844→500→844 를 30프레임, 프레임마다 resize + scroll, 20턴 · 표 든 대화, CPU 6배 감속, 5회 중앙값)

| 지표 | 모바일 390 전 → 후 | 데스크톱 1440 전 → 후 |
|---|---|---|
| React 커밋(다시 그리기) | **30 → 0** | 30 → 0 |
| 이벤트 처리 시간(동기 합) | 28.2 → 8.9ms | 25.7 → 10.4ms |
| 프레임 시간 중앙 / 최대 | 33 / 46 → 33 / 40ms | 34 / 38 → 33 / 39ms |
| 루트 높이가 보이는 영역을 따라감 · 문서 scrollTop | 예 · 0 → 예 · 0 | 예 · 0 → 예 · 0 |

- 커밋 수는 5회 모두 같다(30 · 0). React 커밋은 DevTools 전역 훅으로 셌다(운영 코드에 측정 코드 없음)
- 헤드리스는 iOS 키보드의 레이아웃 · 페인트를 재현하지 못해 프레임 시간 차이는 작다 — **체감은 실기기로 확인해야 한다**
- 화면 모양 변화 없음 : `before/` · `after/` 의 `*-thread.webp`

### 사용자 확인 (iPhone Safari)

1. 긴 대화(답이 여러 개)를 연다
2. 입력칸을 눌러 키보드를 열고, 화면 빈 곳을 눌러 닫기를 몇 번 되풀이한다
3. 입력칸과 헤더가 키보드를 바로 따라오는지(전보다 덜 끊기는지), 헤더가 위로 밀려 사라지지 않는지 본다

원자료 : `before/measure.json` · `after/measure.json`(5회 원값 포함)
