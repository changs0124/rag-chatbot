# after — 3차 (비판 검토 3회 반영본)

세 번 틀린 원인이 전부 같다: 검증한 명제보다 강한 명제를 문서에 적었다.
이번에는 문서 문장을 그대로 붙이고 바로 아래에 검증을 단다. 두 줄을 나란히 볼 수 있어야 한다.

================================================================
문서> - **이 예외는 조회에만 적용된다.** 쓰기 경로(mapper XML 기준 `<insert>` 6 · `<update>` 10
문서>   · `<delete>` 3. 소프트 삭제는 `<update>` 로 센다)는 `dto` 를 매핑하지 않는다.
검증> XML statement 개수 = insert 6 · update 10 · delete 3
검증> softDelete 는 <update> 태그다 (세는 기준을 문장에 명시한 이유)
      67:	<update id="softDelete">
검증> XML 전체에서 com.ragchatbot.dto 등장 = 1건이고 그것을 쓰는 것은 select 뿐
      backend/src/main/resources/mapper/RagDocumentRepository.xml:21:	<resultMap id="summaryResult" type="com.ragchatbot.dto.AdminDtos$DocumentResponse">
      41:	<select id="listAlive" resultMap="summaryResult">

================================================================
문서> 등록은 `entity` 를 통째로 받고(`insert(RagDocument)`),
검증> insert 6건 전부 entity 파라미터
      	void insert(Attachment attachment);
      	void insert(Citation citation);
      	void insert(Conversation conversation);
      	void insert(Message message);
      	void insert(RagDocument document);
      	void insert(User user);

================================================================
문서> **수정·삭제 13건은 전부 `entity` 를 받지 않는다.**
검증> update+delete = 13건
검증> 그중 entity 파라미터를 받는 것 = 0건 (아래는 13건 전수 시그니처)
      	int linkToMessage(@Param("id") UUID id, @Param("messageId") UUID messageId, @Param("userId") UUID userId);
      	int deleteByIdAndUser(@Param("id") UUID id, @Param("userId") UUID userId);
      	int deleteById(@Param("id") UUID id);
      	int deleteByIdAndUser(@Param("id") UUID id, @Param("userId") UUID userId);
      	int updateTitle(@Param("id") UUID id, @Param("userId") UUID userId, @Param("title") String title);
      	int touch(@Param("id") UUID id, @Param("userId") UUID userId);
      	int updateStatus(@Param("id") UUID id, @Param("status") String status);
      	int softDelete(@Param("id") UUID id, @Param("deletedAt") OffsetDateTime deletedAt);
      	void updateName(@Param("id") UUID id, @Param("name") String name);
      	void updatePasswordHash(@Param("id") UUID id, @Param("passwordHash") String passwordHash,
      	void updateTheme(@Param("id") UUID id, @Param("theme") String theme);
      	int demoteAdminsNotIn(@Param("emails") List<String> emails);
      	int promoteAdmins(@Param("emails") List<String> emails);

================================================================
문서> 10건은 식별자와 바뀔 값을 스칼라로 넘기고(`updateStatus(id, status)` · `softDelete(id, deletedAt)`),
문서> 3건은 바뀔 값을 SQL 이 들고 대상 조건만 넘긴다 — `touch` 는 `updated_at = now()`,
문서> `demoteAdminsNotIn` · `promoteAdmins` 는 `role` 값을 SQL 이 들고 이메일 `List` 를 <foreach> 로 펼친다.
검증> SQL 이 바뀔 값을 드는 3건 — 전수. 이 범주에 속하는데 빠진 것이 없음을 확인
      touch:       44:		update conversations set updated_at = now() where id = #{id} and user_id = #{userId}
      demote:      43:		update users set role = 'user'
      promote:     53:		update users set role = 'admin'
검증> 나머지 10건은 바뀔 값을 자바가 넘긴다 (반례 아님) — 예:
      linkToMessage: 30:		update attachments set message_id = #{messageId}
      updatePasswordHash: 72:		update users set password_hash = #{passwordHash}, password_changed_at = #{changedAt}

================================================================
문서> - **규칙의 자리는 `entity/` 가 아니다.** record 6개는 전부 메서드가 없는 값 그릇이라,
문서>   수정·삭제까지 굳이 entity 를 거칠 이유가 없다.
검증> entity record 6개의 메서드 수 (이 문장이 주장하는 전부다)
      Attachment.java      0개
      Citation.java        0개
      Conversation.java    0개
      Message.java         0개
      RagDocument.java     0개
      User.java            0개

      ※ 1·2차에 있던 '그럼 규칙은 어디 있나' 열거절은 삭제했다.
         1차: '규칙이 entity 에'      → 거짓
         2차: '규칙은 service 에'     → 과잉 일반화 (config·dto 에도 있음)
         3차: '권한은 service, 검증은 dto' → 거짓
              권한은 config/SecurityConfig · security/FileAccessTokenService ·
              service/AdminAccessGuard · SQL 의 user_id 조건으로 갈려 있고,
              업로드 MIME·용량·매직바이트 검증은 service/FileService 에 있다.
         결론(entity 를 거칠 이유가 없다)은 record 가 비었다는 사실만으로 성립한다.
         열거절은 논증에 기여하지 않으면서 틀릴 표면적만 늘렸다.
