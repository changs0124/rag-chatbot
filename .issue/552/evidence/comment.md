## #552 리포트 — 첨부 이미지를 문자열로 만들지 않고 흘려 보낸다

**위험은 실제였다.** 가짜 `/responses` 서버 · 운영과 같은 힙(-Xmx665m ≈ 643MB) · SerialGC · 이미지 5장 × 10MB :

| | 변경 전 | 변경 후 |
|---|---|---|
| 스트림 동안 요청 하나가 쥐는 힙 | **66.3MB**(data URL 문자열 5개) | **0.2~0.3MB** |
| 동시 8개 | **OOM** | — |
| 동시 16개(전역 상한) | **OOM** | 정상 |
| 동시 32개 | — | 정상 |
| 힙 123MB 에서 16개 | — | 정상 |

원자료 · 하네스 : `.issue/552/evidence/before/measure.txt` · `after/measure.txt` · `harness.java`(커밋 안 한 측정 전용 하네스 사본)

**변경** — `OpenAiRealService` : 본문 map 의 이미지 자리에 요청마다 무작위 표식만 넣고, `writeBody` 가 본문을 쓰면서 그 자리에 파일을 base64 로 흘려 넣는다(`Base64.getEncoder().wrap`). 없는 파일은 요청을 보내기 전에 실패한다. 업스트림이 받는 본문은 바이트 단위로 같다(66.7MB, 전부터 chunked).

**결정(사용자 승인)** — 착수 때 승인한 「첨부 바이트 상한 + 429」 대신 이 방식. 요청당 메모리가 첨부 크기와 무관해져 상한이 막을 것이 없어 두지 않았다 — 사용자에게 429 가 생기지 않는다.

테스트 : `OpenAiRealImageStreamingBodyTest` 2건(받은 JSON 이 전과 같음 — 이미지 순서 · 패딩 · 표식 모양의 사용자 텍스트, 없는 파일이면 요청 0건) · 지정 범위 141건 통과.
문서 : `backend.md`(「한도를 정하는 것은 메모리가 아니다」는 텍스트만 잰 값이었다는 사실과 이 측정) · `application.yml` · `backend/.env.example` · `api.md` · `ChatService` 주석.

**남은 것(크레딧 필요)** : 5장 × 10MB 본문 66.7MB 가 OpenAI 요청 크기 제한에 걸리는지는 확인 못 했다 — 변경 전부터 같은 크기다.
