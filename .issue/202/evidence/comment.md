## 실측으로 `memswap_limit` 을 정했다 — 스왑 금지(`420m` = `mem_limit`)

운영 VM(`free-vm`, GCE e2-micro, `pd-standard` 30GB)에서 동시 업로드 부하를 걸어 쟀다. 결과가 이슈의 가설을 뒤집었다.

### 측정 조건
- 요청 : 25.9MB 랜덤 바이트를 `Content-Type: image/png` 로 `POST /api/files` (서버 안 `127.0.0.1:8080`, 관리자 토큰)
- 코드 상한 10MB 를 넘으므로 **전부 400 · 저장 0**(힙 적재는 거절 전에 일어나므로 메모리 측정에는 유효)
- 파도 : 동시 **1 → 2 → 4 → 8**, 각 1회 · 사이 20초 휴지 (업로드 레이트리밋 30/분 이내, 총 15건)
- 계측 : app cgroup `memory.current` · `memory.swap.current` · `memory.events(oom)` 1초 간격, `vmstat 1`, 각 요청 HTTP 코드·소요 시간

### before (종전 = `memswap_limit` 미지정, 스왑 +420m 허용)

| 파도 | 소요 시간 |
|---|---|
| c=1 | **39.09초** |
| c=2 | 1.16 · 1.16 |
| c=4 | 1.40 · 1.41 · 1.41 · 1.44 |
| c=8 | 1.99 ~ 2.16 |

- 메모리 피크 **269MB / 420m** · OOM 0
- **swap-out 최대 1페이지** — 두려워한 「업로드가 스왑을 밀어내는 스래싱」은 일어나지 않았다
- 그런데 첫 요청(c=1)이 39초. `vmstat` 를 보면 그 구간 **swap-in 최대 3.8MB/s · io-wait 72%**
- 원인은 swap-**out** 이 아니라 swap-**in** 이었다 : **유휴 중 JVM 힙이 스왑으로 밀려났다가, 한가하다 들어온 첫 업로드가 그 페이지를 45 IOPS 디스크에서 도로 읽어오느라** 39초가 걸렸다. 상주한 뒤로는 동시 8개도 2초대

### after (결정값 = `memswap_limit: 420m`, 컨테이너 스왑 0 · `memory.swap.max=0` 확인)

| 파도 | 소요 시간 |
|---|---|
| c=1 | **1.45초** |
| c=2 | 0.78 · 0.95 |
| c=4 | 0.78 · 0.79 · 0.90 · 0.90 |
| c=8 | 1.29 ~ 1.75 |

- 메모리 피크 **250MB / 420m** · **OOM 0** (스왑을 꺼도 한도에 한참 못 미침)
- 컨테이너 스왑 내내 **0** · swap-in 최대 80KB/s · io-wait 최대 23%
- 첫 요청 39.1초 → **1.45초**

### 결정 근거
- 피크가 269MB / 420m 로 헤드룸이 넉넉해 스왑을 꺼도 OOM 위험이 낮다. 기동 피크도 역사적으로 물리 메모리 안에서 끝났다(스왑 30MiB).
- 진짜로 한도를 넘기면 스왑으로 디스크를 녹이며 질질 끄는 대신 빨리 죽고 재시작한다 — 이슈 본문의 방향과 같다.
