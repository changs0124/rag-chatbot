## 2. 영역별 상세

### 2.1 Frontend

**선택:** React 19 + Vite 8 + Tailwind CSS 4

**이유:**
- 사내 도구라 SEO·초기 로딩이 중요하지 않아 SSR 프레임워크가 필요 없다
- 채팅 UI는 상태가 한 화면에 몰려 있어 전역 상태 라이브러리 없이 훅 하나로 충분하다
- 테마(라이트/다크/시스템)를 CSS 토큰으로 접으면 색에 `dark:` 를 붙이지 않아도 된다

**고려했던 대안:**

| 대안 | 미선택 이유 |
|------|-----------|
| Next.js | SSR·라우팅 규약이 필요 없는데 배포 제약만 늘어난다 |
| 상태 라이브러리(Redux · Zustand) | 전역 상태가 인증·테마 둘뿐이라 Context로 충분하다 |
| 서버 캐시(react-query) | 목록 갱신 지점이 몇 곳 안 되고, 스트리밍은 어차피 직접 다뤄야 한다 |

**감수하는 약점:** 서버 상태 동기화를 직접 한다. 대화 목록 갱신 시점을 코드가 일일이 정해야 한다.

### 2.2 Backend

**선택:** Spring Boot 3.5.16 + MyBatis

**이유:**
- SSE(`SseEmitter`)와 트랜잭션 경계를 표준으로 지원한다
- 스트리밍 구간에서 DB 커넥션을 잡지 않도록 저장을 별도 서비스로 분리하기 쉬웠다
- MyBatis는 SQL이 XML에 그대로 드러나 N+1 같은 문제를 눈으로 잡을 수 있다

**고려했던 대안:**

| 대안 | 미선택 이유 |
|------|-----------|
| Spring Data JPA | 조회가 단순해 매핑 추상화의 이점이 적고, 생성되는 SQL이 안 보인다 |
| WebFlux | 스트리밍 한 경로 때문에 전체를 리액티브로 바꿀 이유가 없다. 실행기 풀로 충분하다 |
| Node.js/NestJS | 팀 숙련도가 Java 쪽이다 |

**감수하는 약점:** Spring Boot 3.5.x는 OSS 지원 종료 트랙이다. 업그레이드 재검토가 백로그에 있다.

### 2.3 Database

**선택:** PostgreSQL + Flyway

**이유:**
- `gen_random_uuid()` 가 코어에 있어 확장 설치 없이 uuid PK를 쓴다
- `timestamptz` 로 시간대 문제를 스키마 단계에서 없앤다
- 부분 유니크 인덱스(`lower(email)`)로 앱을 우회한 삽입까지 막는다

**설계 원칙(템플릿 기본값과 다른 부분):**

| 템플릿 일반 관행 | 이 프로젝트 | 사유 |
|-----------------|------------|------|
| `BIGINT AUTO_INCREMENT` PK | **uuid PK** | 식별자가 URL·SSE 페이로드에 노출된다. 순번이면 총량과 생성 속도가 새어 나간다 |
| 전 테이블 소프트 삭제 | **대부분 hard delete + cascade** | 대화·메시지는 사용자가 지우면 정말 지워야 한다. 감사 대상인 것만 소프트 삭제한다 |
| `DATETIME` | `timestamptz` | 시간대를 값에 담는다 |
| utf8mb4 | UTF-8 (기본) | MySQL 전용 개념이다 |

### 2.4 LLM · Vector DB

**선택:** OpenAI Responses API + OpenAI Vector Store

**이유:**
- 파싱·청킹·임베딩·인덱싱·검색·**인용 생성**을 한 번에 얻는다
- 특히 인용(`file_citation` annotation)이 크다. 본문 어느 구간이 어느 파일에서 왔는지 모델이 직접
  표시하므로, 각주를 프롬프트로 시키고 파싱하는 방식의 환각 위험을 피한다

**고려했던 대안:**

| 대안 | 미선택 이유 |
|------|-----------|
| pgvector 자체 구축 | 저장 비용은 아끼지만 파싱·청킹·임베딩·**인용 추적**을 전부 직접 만들어야 한다. 인용이 가장 비싸고, 자체 구현은 환각 각주 위험을 새로 만든다 |
| gpt-oss 자체 호스팅 | 텍스트 전용이라 이미지 첨부가 죽고, `file_search` 는 모델 기능이 아니라 플랫폼 툴이라 RAG 계층이 통째로 사라진다 |
| 데이터 공유 무료 티어 | 프롬프트·응답이 학습에 쓰인다. 사내 문서를 다루는 파이프라인에 쓸 수 없다 |

**감수하는 약점 — 전환 조건을 미리 적어 둔다.** 아래 중 하나가 실제로 발생하면 자체 구축을 재검토한다.

- 벡터 저장이 수 GB를 넘어 저장료가 눈에 띌 때
- 사내 문서의 외부 상주가 컴플라이언스로 막힐 때
- 검색 품질이 안 나와 청킹 전략·리랭킹을 직접 만져야 할 때

전환 시 가장 비싼 항목은 저장소가 아니라 **인용 재구현**이다. 예산에 그 몫을 넣는다.

### 2.5 인프라/배포

**선택:** 프론트 Vercel · 백엔드 컨테이너

**구성:**
- 프론트 : 정적 번들. `frontend/vercel.json` 에 SPA 리라이트. 환경변수는 `VITE_API_BASE_URL` 하나
- 백엔드 : `backend/Dockerfile`. `PORT` 자동 대응이라 호스트를 가리지 않는다
- 모니터링 : **없음.** 프론트 `ErrorBoundary` 에 연결 지점만 있고 콘솔 기록뿐이다

**미결** : 백엔드 호스트를 정하지 않았다. **첨부 영속 볼륨을 붙일 수 있는 곳**이어야 하고,
못 붙이면 `FileStorage` 를 S3 구현으로 교체해야 한다.

| Node.js | 프론트 빌드·테스트 | 24.x (`.nvmrc` · `engines.node` 양쪽에 선언) |

| Maven Wrapper | 의존성·빌드 | 저장소 동봉 |
| npm | 프론트 의존성 | Node 동봉 |

**런타임 버전이 두 곳 이상에 선언된다.** `.nvmrc` 와 `frontend/package.json` 의 `engines.node` 가
갈리면 Vercel은 후자로 빌드하므로 CI가 통과해도 배포만 다른 런타임을 쓴다. 실제로 있었던 일이라
`scripts/check-runtime-versions.sh` 가 대조한다.

## 4. 리스크

| 기술 | 리스크 | 대응 방안 |
|------|--------|---------|
| OpenAI Vector Store | 저장 용량 비례 과금. 문서가 늘면 월 비용이 선형 증가 | 실측 배율부터 잰다. 전환 조건을 2.4에 명시 |
| OpenAI 모델 | `gpt-4o` 는 노후 라인. 예고 없이 deprecation 공지가 날 수 있다 | `OPENAI_MODEL` 이 env로 빠져 있어 코드 변경 없이 교체 가능 |
| Spring Boot 3.5.x | OSS EOL 트랙 | 업그레이드 재검토가 백로그 상단 |
| 단일 인스턴스 | 수평 확장 시 레이트리밋·동시성 상한이 무력화 | 공유 저장소(Redis 등) 도입 여부를 확장 시점에 결정 |
| 로컬 디스크 첨부 | 볼륨 없으면 재시작마다 소실 | 호스트 선정 시 볼륨 가능 여부를 필수 조건으로 |
| 관측 도구 부재 | 장애 재현 근거가 없다 | REQ-OPS-002의 상관 ID가 최소 대응. 도구 도입은 별건 |
