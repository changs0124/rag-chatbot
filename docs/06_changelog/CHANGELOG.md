## [Unreleased]

### Fixed
- **base 가 `main` 이 아닌 PR 에서 CI 7잡이 하나도 돌지 않았다(#161).** `ci.yml` 의
  `pull_request: branches: [main]` 을 뺐다. `pull_request` 의 `branches:` 는 head 가 아니라
  **base** 를 필터해서, 다른 PR 브랜치 위에 쌓은 PR 은 트리거 자체가 걸리지 않았다.
  **더 나쁜 것은 그게 빨간불로도 안 보였다는 점이다** — 필터에 걸린 워크플로는 실패도 pending 도
  아닌 **「없음」** 이라 체크 목록에 흔적이 없다. Vercel 하나만 green 으로 남아
  `gh pr checks` 와 GitHub 화면이 **「통과」로 읽혔다.**

  2026-09-11 PR #160(이슈 #156)을 PR #157 위에 스택으로 올렸을 때 실제로 그랬다. 머지 직전
  검토에서 잡아 `gh workflow run ci.yml --ref …` 로 손수 돌리고 7잡 통과를 확인한 뒤 머지했다 —
  **못 잡았으면 게이트를 한 번도 안 거친 코드가 `main` 에 들어갔다.**

  **`types:` 에 `edited` 를 더하는 안은 고르지 않았다.** base 를 `main` 으로 재지정하는 시점에는
  돌지만 **스택으로 있는 동안에는 여전히 0잡**이라 구멍이 그대로 남는다. 스택 PR 자체를 금지하고
  문서에만 적는 안도 고르지 않았다 — 이번 사고가 바로 사람이 기억해야만 막히는 종류였다.

  **러너 비용은 반대 근거가 되지 않는다.** 2026-09-11 공개 전환으로 standard runner 분이
  무료다 — 보안 잡을 주 1회에서 변경마다로 되돌린 #135 와 같은 근거다.

  **`push` 트리거의 `paths-ignore: ['.issue/**']` 는 건드리지 않았다.** 의도된 것이고 사유가
  주석에 있다.
- **`FRONTEND_MIN` 을 머지 시점 실측인 115 로 잡았다.** #154 와 #156 이 **각각** 111 → 113 으로
  올렸는데(서로 다른 테스트 2건씩), 같은 줄을 같은 값으로 바꾸는 변경이라 **git 이 충돌 없이
  합쳤다.** 둘 다 들어온 뒤 실측은 115 인데 파일은 113 으로 남았고, 게이트는 「실측 ≥ 하한」만
  보므로 **그대로 통과했다** — 래칫이 2건만큼 헐거워진 것을 아무도 모른다.
  각 PR 의 「111 → 113」 서술은 **그 PR 단독으로는 맞다.** 합산이 안 되는 것이 함정이다.
  **같은 줄을 여러 PR 이 같은 값으로 고치는 파일은 머지 뒤 실측으로 다시 잡아야 한다.**
- **로고 컴포넌트의 접근성·API·정렬 결함 셋을 고쳤다(#154).** 셋 다 #151 이 만든 것이고 원인은
  하나다 — 컴포넌트 API 와 접근성을 덜 다듬은 채 배치했다.

  **모바일 기본 화면에 접근 가능한 브랜드 이름이 0개였다.** 헤더 마크를 무조건 `aria-hidden` 으로
  두고 "드로어를 열면 사이드바 로고가 같은 이름을 읽어 준다"를 근거로 삼았는데, **그 근거는 드로어가
  열렸을 때만 참이다.** 닫혀 있으면 데스크톱 사이드바는 `display:none` 이라 트리에 없고 드로어는
  `{sidebarOpen && …}` 라 DOM 에 아예 없다 — 화면에 보이는 유일한 로고가 숨겨져 있었고 헤더가
  읽어 주는 것은 대화 제목뿐이었다. `decorative={sidebarOpen}` 으로 **열림 상태에서만** 장식이 된다.
  열림 상태의 장식은 그대로 필요하다 : 드로어에 `aria-modal`·inert 가 없어 헤더가 트리에 남으므로
  끄면 「디인사이트」가 두 번 읽힌다. 드로어 전반에 `aria-modal`/inert 를 주는 더 정석적인 방법도
  있으나 **그건 드로어 전체를 건드리는 별개 작업이라 여기서 하지 않았다.**

  **`className` 기본값은 도달하지 않는 죽은 코드이자 함정이었다.** 호출 3곳이 전부 className 을
  넘겨 `??` 오른쪽이 실행되지 않았고, 게다가 병합이 아니라 **교체**라 앞으로 `className="md:hidden"`
  같은 크기 없는 값을 넘기면 `h-`/`w-` 가 통째로 사라진다 — width/height 없이 viewBox 만 있는 SVG 는
  `width:auto` = 100% 라 부모 폭 전체로 부푼다. **지금 깨지는 화면은 없었다.** 필수 prop 으로 바꿔
  타입이 잡게 했고, 호출부가 이미 전부 넘기므로 호출 코드는 한 줄도 바뀌지 않았다.

  **사이드바 좌측 기준선이 셋이었다**(로고 16px · 「새 대화」 24px · 대화 목록 20px). 24·20px 은
  #151 이전부터 있었고 **#151 이 16px 을 하나 더 얹었다.** 그래서 #151 이 만든 것만 되돌려 로고를
  `px-6`(24px)으로 보냈다 — 바로 아래 「새 대화」와 맞는다. **20px 은 건드리지 않았다** : 이 이슈가
  만든 것이 아니고, 목록 항목은 hover 배경이 있어 기준이 다르다.

  덤으로 `WORDMARK` 의 `key={d.slice(0, 24)}` 를 인덱스로 바꿨다. 재정렬·필터·삽입이 없는 모듈
  상수라 인덱스가 정확하다. **접두 충돌은 없었다** — 7개를 실제로 출력해 서로 1~2번째 글자에서
  갈리는 것을 확인했다. 충돌을 고친 게 아니라 근거 없는 키를 없앤 것이다.

  **테스트 2건을 붙였다.** `Logo` 는 `LoginPage.test.tsx` 를 통해 이미 간접 렌더되고 있었지만
  **단언은 0건**이었다. 새 케이스는 클래스가 아니라 **속성 존재 여부**를 본다(`toHaveClass` 는
  이 저장소에 여전히 0건이다) — 드로어 닫힘/열림 양쪽을 성공·실패 쌍으로 두고 변이로 확인했다 :
  항상 장식으로 되돌리면 닫힘 케이스가, 절대 장식이 아니게 하면 열림 케이스가 깨진다.
  jsdom 은 Tailwind 를 적용하지 않아 `hidden md:block` 사이드바가 트리에 남으므로 **헤더(banner)로
  범위를 좁혀** 잰다. 케이스 2건이 늘어 `FRONTEND_MIN` 을 111 → **113** 으로 올렸다.

  **정렬 말고는 화면에 드러나지 않는다** — 나머지 셋은 접근성 속성 · 타입 · React key 라 캡처로
  비교할 것이 없다. 그쪽 회귀 보호는 위 테스트가 맡는다.
- **팔레트 교체가 놓친 토큰 밖 색 셋을 고쳤다(#155).** #151 은 `index.css` 의 토큰만 갈아끼웠고
  **토큰 밖에 직접 박힌 색은 훑지 않았다.** 세 자리가 남았는데 전부 #151 이전부터 있었다.

  **드롭 오버레이가 라이트에서 AA 미달이었다.** `bg-black/30` + `text-white` 는 **다크 전제로 쓴
  스크림**인데, 라이트에서는 검정 30% 가 밝은 회색(`rgb(173,174,176)`)이 되어 그 위 흰 글자가
  **2.10~2.36**, 흰 점선이 **1.71~1.87** 이었다(기준 4.5 / 3.0). #151 이 바탕을 `#FAF9F5` →
  `#F7F9FB` 로 밝히면서 악화되는 방향으로 움직였다. `bg-canvas/85` + `text-ink` + `border-accent`
  로 바꿔 글자 **12.70**(라이트)/14.86(다크), 점선 **4.95**/7.89 가 됐다. 불투명도는 85~95 가
  사실상 같은 값이라(아래 면이 canvas 와 가깝다) 뒤가 비치는 85 를 골랐다.

  **`text-amber-400` 은 `frontend/src` 에 남은 유일한 Tailwind 팔레트 색이었다.** 다만
  **이슈가 제안한 교체 둘은 실측해 보니 둘 다 지금보다 나빴다** — 이 패널(`bg-black/60` +
  `text-white`)은 테마와 무관한 **고정 어두운 섬**이라, 최악(흰 이미지) 기준으로 `highlight` 는
  **2.45** 로 아이콘 기준 3.0 에 미달하고(종전 amber 는 3.44 로 통과), 테마 의존인 `danger` 는
  라이트의 `#C0392B` 가 어두운 패널에 얹혀 **1.06** 이 된다. 그래서 색만 바꾸지 않고 **스크림을
  `bg-black/60` → `/75` 로 함께 내려** `text-highlight` 를 **4.43** 으로 올렸다. 대가로
  `highlight` 의 「배경 전용」 규칙을 「배경 + **어두운 고정 스크림 위 아이콘**」으로 넓혔고,
  근거 수치를 `design-system.md` 「토큰 밖 겹침 — 실측」에 새 절로 남겼다.

  **`MyPage` 오류 배너만 `danger-soft` 를 안 쓰고 있었다.** #151 이 `AdminPage` 의 같은 모양
  배너를 고치면서 **같은 자리가 하나 더 있는 것을 놓쳤다.** 다만 이건 대비 개선이 아니다 —
  `bg-surface` → `bg-danger-soft` 로 대비는 오히려 **4.79 → 4.64**(라이트) · **5.63 → 5.22**(다크)
  로 내려간다. 둘 다 4.5 를 넘으므로 접근성 회귀는 아니고, 일관성 수정이다. 숨기지 않고 적는다.

  **게이트도 테스트도 만들지 않았다.** 이슈는 "Tailwind 팔레트 색 0건인지 **재확인**" 만 요구했고,
  #149 에서 세운 "근거가 한 건뿐일 때 게이트를 만들지 않는다" 를 따랐다 — `grep` 으로 확인만 했다
  (`frontend/src` 0건). 세 자리 전부 클래스 문자열이라 단언할 층위도 아니다(이 저장소는
  `toHaveClass` 가 0건이다). 회귀 보호는 전후 캡처와 위 측정표가 맡는다.
- **`color-scheme` 과 `theme-color` 가 앱 테마 설정을 따르게 했다(#156).** 테마의 정본은
  `data-theme` 하나인데 **이 둘만 OS 설정을 직접 보고 있었다.** OS 가 다크인 기기에서 앱 설정을
  「라이트」로 바꾸면 화면은 라이트인데 **스크롤바 · `<input>` 기본 UI · 주소창만 다크로 남았다.**

  **새 규칙이 아니라 이미 있는 규칙을 어긴 자리였다.** `CONVENTIONS.md` 「스타일」이 이미
  "`prefers-color-scheme` 를 직접 참조하지 않는다 — 시스템 설정 해석은 `ThemeProvider` 가 단독으로
  한다" 고 적어 뒀고, `frontend/src` 전체에 `dark:` 접두가 0건인 것도 그 규칙을 지킨 결과다.
  예외가 딱 둘 남아 있었다.

  `color-scheme` 은 `:root` 에 `light dark` 로 박혀 있었다. **이건 값이 아니라 「UA 가 골라라」는
  위임**이고 UA 는 OS 를 본다. 이 앱은 답을 이미 알고 있으므로 `:root { color-scheme: light }` ·
  `:root[data-theme="dark"] { color-scheme: dark }` 로 알려 준다.

  `theme-color` 는 `media="(prefers-color-scheme: …)"` 로 갈린 `<meta>` 두 개였다. **미디어쿼리로는
  `data-theme` 을 따라갈 수 없다.** `<meta>` 를 하나로 줄이고 `ThemeProvider.applyTheme` 이
  `--c-canvas` 를 읽어 `content` 를 갱신한다. **색 값을 JS 로 복사해 오지 않는다** — `data-theme` 을
  바꾼 뒤 그 상태의 토큰을 읽으므로 정본은 여전히 `index.css` 다. HTML 에 남은 값은 JS 가 돌기
  전까지만 쓰이는 **초기값**이고, 그 사실을 `design-system.md` 「색 값을 들고 있는 파일」과
  `CONVENTIONS.md` 양쪽에 적었다.

  **테스트에도 색 값을 적지 않았다.** 적으면 색을 든 네 번째 자리가 생긴다. 대신 테스트가 토큰을
  심고 `<meta>` 가 **그것을 따라오는지** 라는 배선을 단언한다. 변이로 확인했다 — `content` 갱신을
  빼면 두 케이스가 모두 깨진다. `color-scheme` 쪽은 jsdom 이 `index.css` 를 적용하지 않아 단언할
  수 없어 **캡처가 맡는다.**

  **이 PR 은 #153 위에 쌓았다.** #153 이 바로 이 문단에 "`theme-color` 는 OS 설정을 본다(#156)" 는
  문장을 새로 넣어 뒀고, main 에서 따면 그 문장을 고칠 수가 없다. 코드와 문서를 한 번에 맞추려면
  같은 줄기 위에 있어야 한다.

### Changed
- **#151 이 남긴 문서↔코드 어긋남을 맞췄다(#153).** #151 머지 뒤 병렬 검증 에이전트 넷으로 전수
  대조했더니 문서가 **스스로와 모순되는 곳**이 여럿 나왔다. 원인은 하나다 — 리뷰 반영 커밋에서
  코드를 더 고치면서 문서의 대응 문장을 같이 안 고쳤고, `frontend.md` 는 애초에 #151 diff 에
  넣지 않았다.

  **「색 값을 들고 있는 파일도 `index.css` 하나뿐」이 거짓이었다.** 같은 #151 이 만든 `Logo.tsx` 가
  브랜드색 7개를 들고 있었고 `index.html` 의 `theme-color` 2개도 있었다. 주장이 쓰인 PR 이
  바로 반례를 만든 셈이다. 로고 색을 토큰으로 빼지 **않은** 결정 자체는 옳다(토큰은 `data-theme` 으로
  뒤집히는데 CI 색은 고정이어야 한다) — 문제는 그 예외가 어디에도 없고 `CONVENTIONS.md` 의
  「색은 토큰으로만」과 정면으로 부딪힌 것이다. 예외를 양쪽에 명시하고, **`#0070B5` 와 `#41BAE9` 가
  `index.css` 와 `Logo.tsx` 두 곳에 있다는 사실**을 경고와 함께 적었다 — 한쪽만 고치면 문서의
  「accent = 접힘면 최암부의 실측 픽셀」 주장이 조용히 거짓이 되고 게이트 셋은 전부 통과한다.

  **「손댄 컴포넌트 둘」은 셋이었고 분류도 틀렸다.** `ConfirmModal` 이 빠져 있었고, 그건
  「의미가 틀렸던 토큰」이 아니라 **재도색이 강제한 변경**이다. 셋의 성격이 각각 다르므로 표로 나눴다.

  **문서가 설명하는 파비콘 SVG 가 저장소에 없었다.** #151 이 `gradientUnits` 함정까지 자세히 적어
  놓고 정작 그 파일을 커밋하지 않아, `favicon-source.png` 를 저장소 안 자산만으로 재생성할 방법이
  없었다. 계획 단계에서는 `logo-mark.svg` 를 커밋할 예정이었는데 구현이 인라인 SVG 로 바뀌면서
  그 문단만 주인을 잃은 것이다.

  **처음에는 그 SVG 를 만들어 커밋했다가 되돌렸다.** 커밋해 보니 `Logo.tsx` 와 D 마크 경로를
  글자까지 똑같이, 브랜드색 6개를 그대로 중복해서 들고 있었고 — **만든 지 몇 시간 만에 오렌지
  경로가 한 글자 갈라졌다**(리뷰에서 `Logo.tsx` 쪽 중복 `Z` 만 지웠다). 같은 커밋에서 "색 값이
  두 곳에 살면 한쪽만 고쳐지고 게이트는 전부 통과한다"고 경고문을 쓰면서 그 위험을 한 단계

- **`main` 에 required status checks 를 걸었다(#166).** 종전에는 레거시 branch protection 도

  전에는 이 설정을 걸 수조차 없었다 — 스택 PR 에서 잡이 아예 안 떠서 필수 체크가 영영 pending 으로
  남아 merge 를 **완전히** 막았을 것이다.

  **`docker` 를 빼지 않았다.** 빼도 잡은 어차피 모든 PR 에서 도니 **걸리는 시간이 전혀 줄지 않고**,
  얻는 것 없이 Dockerfile 게이트만 잃는다. 공개 전환으로 러너 분이 무료라 비용 근거도 없다(#135).
  **Vercel 은 넣지 않았다** — #161 에서 「Vercel 만 green」이 오독의 원인이었고, 외부 앱 체크는
  배포가 건너뛰어지면 아예 보고되지 않아 필수로 걸면 merge 를 영영 막는다.

  **관리자 우회는 남겨 두었다.** 취향이 아니라 구체적 파손을 피한 것이다 — required checks 는
  PR merge 뿐 아니라 **그 브랜치로의 직접 푸시도 막는데**, 증거 미러 커밋은 `.issue/**` 만 바꿔
  `paths-ignore` 로 CI 를 건너뛰므로 **체크가 영영 붙지 않는다.** 관리자까지 강제하면 그 푸시가
  영구 차단되고 탈출구는 보호를 통째로 끄는 것뿐이라, 그 순간 모든 게이트가 같이 사라진다.
  우회를 남겨도 게이트는 산다 — 관리자에게도 merge 상태가 `BLOCKED` 이고 우회는 `--admin` 이라는
  별도의 명시적 동작이다. **strict(최신 `main` 위에 있어야 한다)도 껐다** : 증거 미러 커밋이
  `main` 에 직접 올라가므로, 켜면 증거를 푸시할 때마다 열린 PR 전부가 낡아져 매번 rebase 를 요구한다.

  **레거시 branch protection 이 아니라 ruleset 을 골랐다.** 우회 주체를 불리언이 아니라 명시적
  목록으로 적을 수 있고, 레거시 API 는 수정할 때마다 전체 객체를 다시 PUT 해야 해서 다른 설정을
  실수로 지우기 쉽다. 대신 확인 명령이 바뀐다 — `branches/main` 의
  `.protection.required_status_checks.enforcement_level` 로는 **ruleset 이 안 보여** `off` 로 나온다.
  정본은 레거시와 ruleset 을 둘 다 모아 주는 `gh api repos/changs0124/rag-chatbot/rules/branches/main` 이다.

  **API 응답이 아니라 실제 merge 거부로 검증했다.** #161 이 「API 만 보고」 새어 나간 전례가 있다.
  일부러 문서 참조를 깨뜨린 PR(`static` 잡 실패)을 만들고, **관리자 우회를 뺀 동일 규칙**을 버릴
  브랜치에 걸어 `gh pr merge` 를 실제로 시도해 `the base branch policy prohibits the merge` 거부를
  받았다. 관리자 우회가 켜진 `main` 에서 시도하면 우회가 적용돼 그냥 성공하므로 아무것도 증명하지

  보고되는 체크 이름과 글자까지 일치하는지도 기계적으로 대조했다(틀리면 영영 pending 이 된다).

  **필요성은 실측으로 증명돼 있었다.** `#138` 의 버그(`printf` 가 인자를 버리던 것)는
  `bash -n` 을 통과했고 shellcheck 만 **SC2182** 로 잡는다. 이 게이트를 넣은 뒤 그 버그를
  일부러 되살려 보니 정확히 그렇게 갈렸다.

  **기존 경고 12건을 전부 처리하고 넣었다** — 하한을 두면 그 아래가 조용히 쌓여, 게이트가
  빨간불이 되는 날 아무도 안 본다. 처리 내역 :
  - **고침 2** : `check-doc-versions.sh` 의 `${name}` 중괄호(SC1087) · `check-case-floor.sh` 의
    `# shellcheck source=` 경로를 저장소 루트 기준으로 정정(SC1091 이 `-x` 로 해소됨)
  - **배열 전환 3** : `check-doc-refs.sh`·`check-doc-sections.sh` 의 `$paths` 를 문자열에서
    배열로 바꿨다(SC2086). 부수 효과로 **경로에 공백이 있어도 견딘다** — 동작은 전과 동일함을

  - **근거 있는 억제 6** : 백틱을 리터럴로 찾는 정규식 3곳(SC2016) · `summary()` 뒤의 안전망
    `exit` 2곳(SC2317) · 우리가 만든 고정 파일명에 대한 `ls` 1곳(SC2012).

  **`bash -n` 과 달리 도구가 없을 수 있다.** `ubuntu-latest` 러너에는 기본 설치돼 있고,
  로컬에 없으면 `check-all.sh` 가 `skip()` 으로 등록해 **"통과"가 아니라 "모름"** 으로 찍는다.
- **셸 구문 검사 게이트를 추가했다(#136).** `scripts/check-shell-syntax.sh` 가 추적되는 셸
  전부(`git ls-files '*.sh'` + `case-floors.env`, 현재 9개)에 `bash -n` 을 돌린다.
  `check-all.sh` 와 CI `static` 잡 양쪽에서 **제일 먼저** 돈다.

  **왜 필요했나** : 이 저장소의 품질 게이트는 `scripts/check-*.sh` 가 만든다. 그런데 정작
  그 스크립트들을 보는 게이트가 하나도 없었다 — **게이트를 만드는 코드가 아무 게이트도 받지
  않는 상태**였다. `#133` 에서 `deploy.sh` 를 고치는 동안 드러났고, `#138` 의 버그가 살아남은

  실제 배포를 시도하는 순간에야 드러난다.

  **목록을 손으로 관리하지 않는다.** 상수로 개수를 박으면 새 스크립트를 더할 때마다 같이

  재현된다. 스크립트가 **검사한 개수를 출력**해 대상이 0이 되어도 "통과"로 보이지 않게 했다.

  무상 패치였다. 4.0 을 건너뛰고 **4.1** 로 간 것은 4.0 이 2026-12 에 끝나 몇 달 뒤 같은 일을 반복하기
  때문이다. **동작은 바뀌지 않았다** — 184건 전부 그대로 통과하고 응답 계약도 6필드 4곳 일치다.

  **`java.version` 이 17 그대로여서 `javax` → `jakarta` 대공사는 없었다.** 실제로 손댄 것은 Boot 4 의
  **모듈 분해**를 따라가는 일이었다. Boot 3 에서 `spring-boot-autoconfigure` 한 덩어리에 있던 자동설정이
  기능별 모듈로 쪼개져, **의존성에 없으면 조용히 자동설정만 사라진다.**

  - **Flyway 가 이 함정을 정확히 밟았다.** `flyway-core` 는 그대로 있는데 마이그레이션을 돌려 줄
    자동설정이 없어 빈 스키마로 떠서 `relation "users" does not exist` 로 **184건이 전부 죽었다.**
    라이브러리가 있으니 컴파일도 통과했다 — `spring-boot-starter-flyway` 로 바꿔 해결했다.
  - `@SpringBootTest` 가 `TestRestTemplate` 을 더 이상 자동 제공하지 않는다. `spring-boot-resttestclient`
    모듈과 `@AutoConfigureTestRestTemplate` 을 명시했다(그 자동설정이 `RestTemplateBuilder` 를 참조해
    `spring-boot-restclient` 도 테스트 스코프로 필요했다). **184건을 새 `RestTestClient` 로 갈아엎지 않았다** —
    런타임 교체가 목적이지 테스트 재작성이 목적이 아니다.
  - `spring-boot-starter-web` → `spring-boot-starter-webmvc`, `UserDetailsServiceAutoConfiguration` 이
    `org.springframework.boot.security.autoconfigure` 로 이동
  - Jackson 2 → 3 : `com.fasterxml.jackson.databind` → `tools.jackson.databind`. **`OpenAiRealService`
    한 파일뿐이었고 `ObjectMapper`·`JsonNode` API 는 그대로였다**
  - Testcontainers 1 → 2 : 아티팩트가 `postgresql` → `testcontainers-postgresql` 로 개명. `PostgreSQLContainer`
    클래스 경로는 그대로였다
  - MyBatis starter 3.0.5 → 4.1.0
  - **`postgresql.version` 수동 고정을 뺐다.** CVE-2026-54291 때문에 `42.7.13` 을 박아 뒀는데 4.1.1 BOM
    관리분이 정확히 같은 값이다. 남겨 두면 앞으로 BOM 이 더 올려도 낮은 값에 묶어 두게 되어 **원래
    고정한 이유(보안)와 반대로 작동한다.**

  **검증되지 않은 경로가 하나 있다.** Jackson 을 바꾼 `OpenAiRealService` 의 SSE 파싱은 `APP_MODE=live`
  전용이라 mock 테스트가 밟지 않는다. 컴파일과 코드 대조로만 확인했고, 실 연동 검증은 실 OpenAI 키가
  생긴 뒤 백로그 「높은 우선순위」의 실 연동 항목에서 함께 봐야 한다.

- **Spring Boot 3.5 의 지원 종료 사실을 문서에 박았다(#47).** 세 곳이 똑같이 "OSS EOL 트랙 — 업그레이드
  재검토가 필요하다" 로 적혀 있었다(`backlog.md` · `requirements.md` · `overview.md`). **"재검토" 는
  아직 판단할 여지가 있다는 뜻인데 기한은 이미 지났다** — 3.5 의 OSS 지원은 2026-06-30 에 끝났고
  `pom.xml` 이 물고 있는 `3.5.16` 이 마지막 무상 패치다(2026-06-25, EOL 5일 전). `3.5.17` 은 없다.

  **하나의 사실이 세 문서에 흩어져 같이 낡아 있었다.** 어느 하나만 읽어도 "여유가 있다" 고 판단하게 되므로
  셋을 함께 고쳤다. 날짜·마지막 패치 버전·권장 경로(4.0 이 아니라 **4.1**)·근거 링크를 박아, 다음에 읽는
  사람이 검색 없이 판단할 수 있게 했다.

  **위험은 "이미 막혔다" 가 아니라 "막히는 시점을 우리가 못 고른다" 다.** `deps (백엔드 의존성 취약점)`
  잡은 지금 통과하고 있지만, 3.5.x 에 새 CVE 가 공개되면 올릴 버전이 없어 고칠 방법 없이 막힌다. 시점을
  정하는 것은 외부다. 그래서 항목을 「보통」에서 **「높은 우선순위」로 올렸다** — 기존 상위 둘은 실 OpenAI
  키가 없어 손댈 수 없는 반면 이건 막힌 것이 없다. 실제 업그레이드는 #48 로 나눴다.

### Fixed
- **라우팅 단계에서 거절되는 요청을 500 이 아니라 404 · 405 · 415 로 내린다(#45).** #38 이 본문 파싱 쪽
  절반을 400 으로 잠그면서 나머지 절반을 `api.md` 에 405·415 가 없다는 이유로 남겨 뒀다. 그 절반을 닫는다.

  **명세를 먼저 정하고 실측했다.** `api.md` 오류 코드 표에 `METHOD_NOT_ALLOWED` · `UNSUPPORTED_MEDIA_TYPE`
  을, 상태 코드 표에 405 · 415 를 새로 정의한 뒤 케이스 3건을 기대값 4xx 로 넣어 돌렸다 — **셋 다 실제로
  500 이었다.** 없는 URL 이 던지는 예외는 `NoHandlerFoundException` 이 아니라
  `NoResourceFoundException` 이었다(Spring Boot 3.2+ 의 정적 리소스 체인).

  **`ResponseEntityExceptionHandler` 를 상속하지 않고 핸들러 셋을 개별로 더했다(10종 → 13종).** 상속하면
  그쪽 기본 구현이 `ProblemDetail`(RFC 7807) 본문을 만들어 **`{code, message}` 응답 계약이 그 경로에서만
  깨진다.** 405 에는 `Allow` 헤더를 함께 실었다 — RFC 9110 §15.5.6 이 MUST 로 요구하고, 없으면 보낸 쪽은
  무엇으로 다시 쳐야 하는지 알 수 없다.

  **405·415 는 403 을 쓰지 않는 P-3 원칙과 충돌하지 않는다.** P-3 가 가리는 것은 리소스의 존재이고,
  이 둘이 드러내는 것은 `api.md` 에 이미 공개된 라우트 형태와 요청 형식이다. `TC-OPS-019~021` 이 잠근다.
  `backlog.md` 의 해당 항목은 이제 남은 절반이 없어 지웠다.

- **문서 업로드 상한을 25MB 로 통일하고 죽은 분기를 되살렸다(#35).** 상한을 말하는 곳이 여덟인데
  숫자가 셋이었다 — 화면과 문서 다섯 곳이 50MB, `application.yml` 이 25MB, yml 주석이 "문서 20MB".
  **그중 사용자가 보는 숫자가 가장 틀렸다.** 30MB 문서를 고른 관리자는 안내를 믿고 올렸다가 원인 모를
  413 을 받았다. 실측 경계는 26,214,400 바이트(25MiB)였다.

  숫자만 맞추면 문제가 남는다. `MB` 상수가 `1024*1024` 라 코드의 `25 * MB` 와 Spring 의 `25MB` 는
  **정확히 같은 값**이고, 같으면 멀티파트가 먼저 걷어차 코드 검사가 여전히 실행되지 않는다.
  그래서 두 한도의 순서를 복구했다 — 코드 25MB < 멀티파트 26MB. 이미지 경로가 10MB < 26MB 로
  처음부터 지키던 구조이고 **문서만 50 > 25 로 뒤집혀 있었다.**

  이제 상한을 넘긴 문서는 413 이 아니라 **400 `용량 초과(최대 25MB)`** 를 받는다. `TC-ADMIN-025` 가
  이 순서를 잠근다 — 413 으로 바뀌면 두 값이 다시 뒤집혔다는 신호다.

- **읽을 수 없는 요청을 500 이 아니라 400 으로 내린다(#38).** `GlobalExceptionHandler` 에 전용 핸들러가
  없는 예외는 요청 잘못이든 서버 잘못이든 전부 `@ExceptionHandler(Exception.class)` 폴백으로 떨어져
  `INTERNAL_ERROR` 가 됐다. 보낸 쪽은 상관 ID 만 받아 무엇을 고쳐야 하는지 알 수 없었고, 단서는 서버
  로그뿐이었다. `api.md` 가 이 경우를 400 으로 규정하고 있어 명세 위반이기도 했다.

  **테스트를 먼저 써서 관찰했더니 새는 경로가 넷이었다** — 깨진 JSON 문법, UTF-8 이 아닌 인코딩,
  빈 본문, 그리고 **경로 변수 타입 불일치**. 마지막 것은 이슈에 후보로만 적었는데 실제로 500 이었다
  (`/api/conversations/not-a-uuid/messages`). 없는 UUID(404)와 UUID 가 아닌 값(400)은 다른 사건이다.

  넷 다 원인이 「클라이언트 입력을 읽을 수 없음」 한 갈래라 `HttpMessageNotReadableException` ·
  `MethodArgumentTypeMismatchException` 두 핸들러가 받는다(8종 → 10종). **예외 메시지는 싣지 않는다** —
  파서 예외에는 본문 조각과 클래스 이름이 들어 있어 폴백과 같은 이유로 노출 대상이 아니다.

  `backlog.md` 가 이 버그를 이미 예측하고 있었다. 그 항목의 나머지 절반(없는 URL · 405 · 415)은
  **`api.md` 상태 코드 표에 405·415 가 아예 없어 명세부터 정해야 하므로** 범위 밖으로 두고 좁혀 남겼다.

- **문서 업로드가 형식을 모를 때 파일 확장자를 본다(#36).** 화면은 `.md` · `.docx` 를 고를 수 있게 열어
  두는데 서버는 `content-type` 으로만 판정해, **같은 파일이 사용자 PC 설정에 따라 되기도 하고 안 되기도
  했다.** 브라우저는 `File.type` 을 OS 의 MIME 레지스트리에서 채우므로 등록이 없으면
  `application/octet-stream` 으로 온다 — Windows 의 `.md`, Office 가 없는 환경의 `.docx` 가 그렇다.

  매직바이트로 푸는 길은 코드가 이미 배제해 두었다(`txt`·`md` 는 시그니처가 없고 `docx` 는 zip 이라
  `PK` 만으로 구분되지 않는다). 그래서 content-type 을 1차로 두고 **형식을 모를 때만** 확장자를 2차로 본다.

  **이 변경의 위험은 검사 해제다.** `image/png` 처럼 형식을 아는데 목록에 없는 것까지 확장자를 봐 주면
  파일명만 바꿔 낸 파일이 통과한다. 신규 5건 중 3건을 이 방어에 썼고(허용 목록 밖 확장자 · 매직바이트
  우회 · 아는 형식의 폴백 금지), 세 건 모두 **고치기 전에 이미 통과**해 기준선이 잡힌 상태에서 고쳤다.

- **케이스 수 하한 `BACKEND_MIN` 167 → 177.** #38 과 #36 이 각각 5건씩 더했다.
  두 PR 이 같은 줄을 **같은 값(172)으로** 바꿔 git 이 충돌 없이 합쳤는데, 둘 다 들어간 뒤의 실측은 177 이다.
  래칫은 `실측 >= 하한` 만 보므로 172 로 남아도 CI 는 영구히 초록이고 **새 케이스 10건이 보호를 받지
  못한다.** 통합 직후 실측값으로 바로잡았다 — 텍스트 충돌이 없다고 의미까지 맞는 것은 아니다.

- **케이스 수 하한 `BACKEND_MIN` 177 → 181(실측).** #35 가 1건, #39 가 3건 더했다.
  이번에는 두 PR 이 같은 줄을 **다른 값(178 · 180)으로** 바꿔 **git 이 충돌로 멈춰 세웠다.**
  위 항목과 반대 경우이며 다루기 쉬운 쪽이다 — 사람이 판단해 합집합 181 로 해소했고,
  merge 후 `clean verify` 실측(181)으로 확정했다. 값이 같아 조용히 합쳐지는 쪽이 위험하다.

### Changed
- **검색 도구가 붙는 턴에 근거 지시를 함께 보낸다(#39).** RAG 근거 부착이 전적으로 모델 재량이었다.
  요청 바디에 `instructions` 도 `tool_choice` 도 없어 기본값 `auto` 로 돌았고, 모델이 file_search 를
  건너뛰면 annotation 이 0건이 되어 **스토어에 분명히 있는 내용을 물어도 「자료 없음」이 뜰 수 있었다.**
  더 나쁜 것은 그 화면이 다른 원인 셋(스토어 미주입 · `vs_` ID 오타 · 인용 추출 실패)과 구분되지
  않는다는 점이다.

  사내 규정·절차처럼 조직마다 다른 내용은 검색 결과에 근거하고 못 찾았으면 먼저 밝히라는 지시를
  싣는다. **강제하지는 않는다** — `tool_choice` 로 file_search 를 강제하면 부착률은 오르지만 단순
  인사말에도 검색이 붙어 턴당 비용과 응답 지연이 는다. 대가는 편차이며, 실 연동에서 부착률을 재 본
  뒤 다시 판단할 자리다(`live-integration.md` 3-2).

  **검색 도구가 붙을 때만 싣는다.** 스토어가 없는데 사내 문서를 찾으라고 지시하면 모델에게 없는
  도구를 쓰라는 셈이라 답변이 어긋난다. 스텁 서버로 실제 요청 바디를 잡아 셋을 잠갔다 — 스토어가
  있으면 실리는지, 없으면 안 실리는지, `tool_choice` 를 보내지 않는지. 마지막 것은 **정책을 강제로
  바꾸는 순간 깨지므로 그때가 눈에 띈다.**

  남은 것 : 스토어 미설정과 「검색했으나 근거 없음」이 화면에서 여전히 구분되지 않는다. 나누려면
  SSE 이벤트 계약을 바꿔야 해 원인이 다른 작업으로 남겼다.

- **live 연동 절차서를 실제로 성립하는 순서로 고쳤다(#34).** 절차서만 따라가면 완주할 수 없었다.
  `backend/.env` 는 dotenv 로더가 없어 `docker compose` 의 `env_file` 밖에서는 읽히지 않는데
  `INDEX.md` · `backend.md` 가 `./mvnw spring-boot:run` 을 정본으로 제시해, `.env` 를 채우고도
  「APP_MODE 미설정」으로 기동에 실패하는 경로가 열려 있었다.

  투입 절차의 순서도 성립하지 않았다. 종전 2-1 은 스토어를 만들며 문서까지 넣으라고 했으나, 문서를
  넣는 유일한 경로가 `OPENAI_VECTOR_STORE_ID` 주입 후 기동을 요구한다. 그대로 따르면 **같은 문서가
  금지한 상태** — 대시보드로 올려 관리 화면에서 보이지도 지워지지도 않는 상태 — 에 도달했다.
  빈 스토어 생성 → ID 주입·기동 → 제품 화면 업로드로 갈랐다.

  준비물 표에 `DB_*` 와 `JWT_SECRET` 을 넣어 「기동을 막는 것」을 셋 → 여섯으로 고치고, 키 발급 위치와
  `vs_` 형식·확인 curl 을 앞머리에 뒀다(링크 0건이던 문서다). 3-1 에 증상→원인 표를 더했다 —
  「자료 없음」 하나에 원인이 넷 몰려 있어 화면만으로는 갈라지지 않는다.
- **도커 이미지 빌드를 Maven Central 가용성에서 떼어냈다(#29).** build 스테이지 베이스를
  `eclipse-temurin:17-jdk-alpine` → `maven:3.9.16-eclipse-temurin-17-alpine` 으로 바꾸고 `./mvnw` 를
  `mvn` 으로 돌렸다. 종전에는 그 베이스에 `mvn` 이 없어 **빌드마다 Maven 배포판 zip 을 Central 에서

  - 도메인 예외(400·404·409·429)는 폴백에 걸리지 않음을 케이스로 잠금 — 폴백이 앞 핸들러를 가로채면 전부 500이 됨
  - SSE 스트림 도중 오류는 대상이 아님. 응답이 이미 시작돼 상태 코드를 바꿀 수 없고 `ChatService` 가 `event: error` 로 따로 처리함
- **세션 슬라이딩 재발급 (FEAT-OPS-003 · REQ-AUTH-005)** — 120분 고정 만료에 갱신 수단이 없어 업무 도중 세션이 끊기면 작성하던 내용이 날아갔음. 남은 수명이 임계(`JWT_REFRESH_THRESHOLD_MINUTES`, 기본 30분) 미만이면 응답 헤더 `X-Refresh-Token` 으로 새 토큰을 보냄
  - 리프레시 토큰을 두지 않음 — 테이블·회전·재사용 탐지가 붙어 작업량이 3~4배인데, 기존 `password_changed_at` 무효화 규칙과 그대로 호환되는 슬라이딩으로 같은 목적을 달성함
  - **CORS 노출 헤더 등록을 케이스로 잠금** — 빠뜨리면 서버는 정상 발급하는데 브라우저가 값을 숨겨 **조용히 아무 일도 안 일어남**. 실패가 눈에 안 띄는 부류라 다른 검사로는 드러나지 않음
  - 프론트는 **두 경로 모두**에서 교체함 — `frontend/src/lib/api.ts` 래퍼와 `frontend/src/lib/endpoints.ts` 의 채팅 스트림. 스트림은 래퍼를 안 거치므로 한쪽만 하면 채팅만 쓰는 사용자는 갱신을 못 받음
  - 임계 `0` 이면 기능이 꺼져 종전 고정 만료로 돌아감(되돌리기 경로도 케이스로 검증)
- **관리자 권한 (FEAT-ADMIN-001 · REQ-ADMIN-004)** — `users.role` 신설(V5). 지금까지 로그인한 전원이 동등해 RAG 문서를 관리할 사람을 구분할 수단이 없었고, 그 때문에 문서 등록 경로 자체를 제품 안에 둘 수 없었음
  - 승격은 환경변수 `ADMIN_EMAILS` 명단으로만. **앱에 권한 상승 API 를 두지 않아** 공격면이 늘지 않고 통제권이 배포 설정에 남음. "첫 가입자 자동 승격"은 DB 초기화 시점에 외부인이 먼저 가입하면 그가 관리자가 되어 기각함
  - **강등을 함께 함** — 승격만 하면 명단에서 지운 계정이 영구히 관리자로 남아 명단이 통제 수단이 되지 못함. 명단을 통째로 비우면 전원 강등이며 그것이 맞는 동작임
  - 역할을 **JWT 클레임에 담지 않음** — 담으면 강등이 토큰 만료까지 반영되지 않음. 인증 필터가 이미 요청마다 사용자 행을 읽으므로 추가 쿼리가 없음
  - 명단에 있으나 미가입인 이메일은 **가입 시점에** 반영함. 기동 동기화는 이미 가입한 계정만 손대므로, 이 경로가 없으면 명단에 미리 넣어 둔 사람이 가입해도 재기동 전까지 일반 사용자임
  - `GET /api/auth/me` 응답에 `role` 추가 — 프론트가 관리 메뉴 노출을 판단할 값. **표시 판단일 뿐 접근 제어가 아님**
- **RAG 문서 관리 (FEAT-ADMIN-002 · REQ-ADMIN-001·002·003)** — 공용 Vector Store 에 문서를 넣는 경로가 제품 안에 없어 OpenAI 대시보드 수동 작업뿐이었음. 규정이 개정될 때마다 개발자가 콘솔에 들어가야 했고, **누가 언제 어떤 문서를 올렸는지 기록이 어디에도 남지 않았음**
  - `rag_documents` 신설(V6) + `GET·POST /api/admin/documents` · `DELETE /api/admin/documents/{id}`
  - 허용 형식이 **채팅 첨부와 반대** — 첨부는 비전 입력용이라 이미지만, 여기는 색인용이라 문서(PDF·TXT·MD·DOCX)만. 매직바이트는 PDF 만 검사함(txt·md 는 없고 docx 는 zip 이라 `PK` 만으로 구분되지 않음 — **검사할 수 없는 형식을 검사하는 척하지 않음**)
  - 최대 50MB. OpenAI 상한(512MB)에 맞추면 요청 하나가 멀티파트 버퍼를 512MB 잡아 단일 인스턴스가 그대로 멎음
  - **소프트 삭제** — 이 저장소에서 유일함. "언제 내려갔는가"가 감사 대상이라 행을 지우면 그 사실이 남지 않음. `uploaded_by` 도 `on delete restrict` 로, 사용자를 지워도 문서 이력이 사라지지 않음
  - 스토어 미설정이면 400 이고 **DB 행을 만들지 않음** — 어디에도 없는 문서가 목록에만 뜨는 상태가 가장 나쁨. Vector Store 연결 실패 시 올린 파일을 즉시 정리함
  - 목록은 `in_progress` 인 행만 상태를 다시 물음. 올린 사람 이름은 **조인으로 함께** 가져옴(N+1 방지)
  - 목업 모드에서도 전 경로 동작. 파일 ID 에 `mock-` 접두를 붙여 실 데이터와 섞이지 않게 함
- **관리자에 의한 비밀번호 초기화 (FEAT-ADMIN-003 · REQ-AUTH-006)** — 비밀번호를 잊으면 복구 경로가 전무했음. SMTP 도입 없이 관리자 발급으로 해결함
  - 임시 비밀번호는 응답에 **한 번만** 실리고 저장되지 않음. 혼동하기 쉬운 글자(`0/O` · `1/l/I`)를 뺀 문자 집합을 씀 — 사람이 눈으로 읽어 옮기는 값임
  - 자기 자신은 대상에서 제외 — 마이페이지에 변경 기능이 이미 있고, 관리자가 자기 세션을 스스로 끊을 이유가 없음

### Fixed
- **관리자 초기화에서 대상의 기존 토큰이 살아남던 것** — `password_changed_at` 을 초 단위로 자르는 기존 규칙은 "같은 초에 발급된 직전 토큰 1개"가 살아남는 틈을 감수하는데, 그 근거가 *"그 토큰의 주인은 방금 비밀번호를 바꾼 본인"* 이었음. **관리자 초기화에서는 그 전제가 깨짐** — 토큰 주인은 다른 사람이고 그 세션을 끊는 것이 기능의 목적임. 여기서는 살려 둘 토큰이 없으므로 경계를 현재 초의 끝으로 밀어 틈을 없앰
- **슬라이딩 재발급 검사 3건이 조용히 실행되지 않던 것** — 임계값이 클래스 단위 프로퍼티라 변형을 중첩 static 클래스로 두었는데, surefire 기본 include 패턴(`**/*Test.java`)에 걸리지 않아 수집조차 되지 않았음. 별도 파일로 분리함. 함께 넣었던 "중첩 클래스가 존재하는가" 검사는 아무것도 검증하지 못하는 가짜 통과였으므로 제거함
- **`frontend/src/lib/stream.test.ts` 의 fetch 스텁이 실물과 갈려 있던 것** — `{ ok, body }` 리터럴이라 `headers` 가 없었고, 응답 헤더를 읽는 코드가 붙는 순간 터졌음. 방어 코드를 넣지 않고 실제 `Response` 를 쓰도록 스텁을 고침

- **관리자 화면 (SCR-ADMIN-001 · 002)** — `/admin` 신설. 백엔드 API 만 있던 상태를 화면으로 마감함

  - 인덱싱 중인 문서가 하나라도 있을 때만 5초 폴링하고 **전부 종료 상태면 멈춤**. 안 멈추면 화면을 열어둔 내내 배경에서 돎

  - 문서 0건은 "검색했는데 없다"가 아니라 **아직 시작하지 않은** 상태임을 문구로 밝힘
  - 삭제 확인이 "이미 나간 답변의 출처 표기는 그대로 남습니다"를 알림 — `citations` 가 영속화돼 있어 실제로 남고, 안 알리면 "지웠는데 왜 아직 보이지"가 됨
