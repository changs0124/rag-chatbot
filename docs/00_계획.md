## 실행 규칙 요약 (가이드 S-1~S-3 발췌)

- **S-1 절대 금지** : 모르는 것을 채우지 않음(모호하면 멈추고 물음) · 확인 안 한 숫자를 판정에 쓰지 않음 · 검증 없이 "완료"라 하지 않음(명령 출력/응답/화면 근거 + 종료 코드 확인) · 버전을 기억으로 답하지 않음(공식 문서 + 확인일) · 기준을 낮춰 통과시키지 않음 · 테스트 skip/게이트 완화 금지 · 스텁/목을 완료로 위장 금지(미결 등재) · 시크릿 비커밋 · 작성과 리뷰를 같은 컨텍스트에서 하지 않음
- **S-2 상시 3** : 완료 판정 없는 항목에 착수 안 함 · 새 테스트는 반드시 한 번 깨뜨려 실패 확인 · 문서와 코드는 같은 커밋/PR에서 움직임
- **S-3 멈추고 물을 것** : 기술 스택 최종 채택 · 플랜 승인 · 비용 발생 · 도메인/계정/시크릿 · 대외 공개 · 법적 문구 · 모호한 요구 · 되돌릴 수 없는 파일 조작 · 승인 범위/AC 변경

| 항목 | 값 |
|------|-----|
| 프로젝트명 | rag-chatbot |
| 유형 | 신규 |
| 규모 | 정식 (1주~1개월) |

## 포함 범위

> 번호 계열 주의 : 이 표의 `R-n`은 **요구**이고, 아래 리스크 표의 `R-n`은 **리스크**로 별개 계열임(요구 R-1~R-11 · 리스크 R-1~R-14로 값까지 전부 겹침). 다른 표에서 리스크를 가리킬 때는 `리스크 R-n`처럼 계열을 앞에 적음.

| 번호 | 항목 | 이 항목이 없으면 무엇이 성립하지 않는가 |
|------|------|------------------------------------------|
| R-1 | RAG 응답 코어 : 질문 → Store 검색 → 출처 포함 답변 | 챗봇의 존재 이유가 없음 |
| R-2 | 입력 4종 : 텍스트 · 파일 첨부 · 카메라 촬영 · 사진(갤러리) 업로드 | 멀티모달 질문이 불가 |
| R-3 | 첨부 이미지 GPT-4o 비전 전달 + 대화에 저장 | 사진 기반 질문이 처리되지 않고 이력에도 안 남음 |
| R-4 | 출처 표기(각주 번호 + 하단 출처 목록) · 무자료 시 "자료 없음 + 추론" 접두 | 신뢰성(R 핵심 요구) 미충족 |
| R-5 | 사용자 인증 : 자체 이메일/비밀번호 로그인 | 사용자별 대화/마이페이지가 불가 |
| R-6 | 마이페이지 : 이름 변경 · 비밀번호 변경 · 테마 변경(라이트/다크/시스템) | 개인화가 불가 |
| R-7 | 사용자별 대화 저장/조회 | 대화 이력 유지가 불가 |
| R-8 | 반응형 웹 UI (Claude/GPT 류 채팅 틀, Supernova로 마감) - PC + 모바일 브라우저 | PC/모바일 사용이 불가 |
| R-9 | 응답 스트리밍(타이핑 효과) | 응답 대기 UX가 저하됨 |
| R-10 | 목업 계층 : `APP_MODE=mock`, 실 연동 인터페이스는 완성 · 응답만 목 데이터 | API KEY/VectorDB 없이 개발·시연이 불가 |
| R-11 | 응답 진행 단계 표시 : 질문 분석 → 참조 문서 검색 → 답변 작성 3단계를 채팅 화면에 실시간 표시(**SSE 개시 이후 구간에 한정** - 첨부 업로드·prepare·429는 범위 외) | 첫 토큰 전 대기가 무반응으로 보이고, RAG가 실제로 문서를 참조했는지 사용자가 알 수 없음 |

# 2단계 - 플랜 (사용자 승인 대기)

## 원칙 (P)

- **P-1** : OpenAI 키·파일 접근은 백엔드 뒤에 둠. 프론트는 자체 API만 호출함(키 비노출)
- **P-2** : OpenAI 호출은 `OpenAiService` 인터페이스 경계 뒤로 격리하고, `APP_MODE=mock`(기본)로 키 없이 전 경로가 동작함
- **P-3** : 인가는 애플리케이션 코드가 전 경로에서 함(`requireOwned`). 남의 리소스는 403이 아니라 **404로 존재 은닉**
- **P-4** : 스키마의 소유자는 마이그레이션 SQL임. MyBatis 매퍼가 스키마를 바꾸지 않음
- **P-5** : 스트림 수명은 SSE emitter가 관장함(MVC async 타임아웃을 끄고 `sse-timeout`이 단독 결정)
- **P-6** : 출처는 DB(`citations` 테이블)에 영속화함. SSE로만 보내 재진입 시 소실시키지 않음(참조 구현 결함 개선)
- **P-7** : 파일 저장은 `LocalFileStorage` 인터페이스 뒤에 둠(S3 등으로 교체 가능). 경로는 서버가 소유하고 소유권 검증 후 서빙함
- **P-8** : 무자료 판정은 Mock/Real 공통 규칙임 - 검색 결과 0건이면 규정 접두("자료 없음 + 추론")를 붙이고 출처를 비움
- **P-9** : 판단이 갈리면 이 원칙으로 되돌아옴. 원칙에 없으면 사람에게 물음
- **P-10** : 진행 단계(R-11)는 **실 스트림 이벤트 또는 서버가 실제로 통과한 코드 경계에만** 근거함. 타이머·인위 지연·추정으로 연출한 단계는 만들지 않고, 근거가 되는 이벤트·경계가 없으면 그 단계를 보내지 않음(S-1 위장 금지 · D-4 연장). 단계 라벨에는 검증되지 않은 수치(검색 건수·파일명 등)를 넣지 않고, **목업 단계는 목 데이터임이 드러나는 전용 문구를 씀**(라이브 라벨을 목업이 그대로 쓰지 않음). **최소 표시 시간은 연출이 아님** - 실제 도달한 단계를 도달 순서대로 최소 350ms 유지해 읽을 수 있게 하는 것은 허용하고(없는 단계 생성·순서 변경은 금지), 서버가 단계 사이에 인위 지연을 넣는 우회는 계속 금지함

## 결정 동인 (D)

- **D-1** : OpenAI 호출이 곧 비용임 → 레이트 리밋 + 목업 기본값이 비용 통제 수단
- **D-2** : 개인 데이터 격리 → 교차 접근 1건이 곧 사고. 소유권 검증이 최우선
- **D-3** : 모바일 우선·사진 업로드 → 카메라 촬영 → 업로드 → 비전 답변이 주 사용 흐름. 반응형 필수
- **D-4** : 출처 신뢰성 → 모든 답변에 출처 또는 "자료 없음"을 명시하는 것이 제품 정체성
- **D-5** : 목업으로 전 흐름을 시연할 수 있어야 함 → 실 연동 인터페이스를 먼저 완성

## 진행 단계(R-11) 이벤트 매핑

> 표시 방식 승인값(2026-07-27) : **한 줄 교체형**(현재 단계 하나만 표시 · 첫 토큰 시 소멸) · **이력 비저장**(휘발, 재조회 시 답변·출처만) · **목업 전용 라벨**(목 데이터임이 화면에 드러남). 이 표가 단계 원천의 단일 출처임(P-10).

| 단계 키 | 화면 라벨(라이브) | 화면 라벨(목업) | 라이브 원천(실 스트림 이벤트) | 목업 원천(통과하는 코드 경계) |
|---------|-------------------|-----------------|-------------------------------|-------------------------------|
| `analyzing` | 질문 분석 중 | 질문 분석 중(목업) | prepare 통과 후 스트림 개시 시점(`meta` 직후) - 라이브·목업 공통 서버 경계 | prepare 통과 후 스트림 개시 시점(`meta` 직후) |
| `searching` | 참조 문서 검색 중 | 목업 코퍼스 조회 중 | `response.file_search_call.in_progress` · `response.file_search_call.searching` | 코퍼스 키워드 매칭 직전 |
| `generating` | 답변 작성 중 | 답변 작성 중(목업) | 첫 `response.output_text.delta` | 첫 `onToken` 직전 |

- **라이브 이벤트명 근거** : OpenAI Responses API 스트리밍 이벤트 공식 문서(확인일 2026-07-27, URL은 `docs/01_기술선택.md` 채택 표). **발생 순서·무검색 시 미발생은 실호출로 확인 전임**(이관-6 · M2)
- **`analyzing`은 서버 경계에서 발생시킴** : 라이브도 `response.created`·`response.in_progress`를 원천으로 쓰지 않음. 요청 본문(이미지 base64 포함) 업로드와 TTFB가 `meta` 이후에 걸려 첫 이벤트까지 표시가 비고, 목업(`meta` 직후 즉시)과도 어긋나기 때문임. 두 이벤트는 단계를 새로 만들지 않는 **도달 확인 신호**로만 두고, 도달 시점 확인은 이관-6 범위에 남김
- **라벨 소유자 · 발행 주체** : 단계 키는 공통이고 **라벨 문자열은 `OpenAiService` 구현이 소유함**(Mock/Real 각자). `ChatService`는 모드를 알지 않고 구현에서 받은 라벨을 그대로 실어 보냄(P-2 경계 유지). `analyzing`은 `ChatService`가 `meta` 전송 직후(= `streamChat` 진입 시점)에 발행하고, `searching`·`generating`은 구현이 자기 경계에서 콜백으로 올림
- **4번째 단계(`citing`, 검색 결과 정리 중) 미채택** : R-11 승인 범위가 3단계이고, 라이브에서 검색 결과 0건에도 `response.file_search_call.completed`가 오는지 미확인이라 채택하면 무자료 분기에서 라이브·목업 표시가 어긋남(P-8 공통 규칙 위반). 필요해지면 이관-6 확인 후 별건 승인으로 추가함
- **범위 한정** : SSE 개시 이후 구간만 다룸. 첨부 업로드(프론트) · prepare 검증 · 레이트리밋 429(스트림 개시 전 동기 응답)에는 단계 표시가 없는 것이 정상 동작임. 업로드 구간 표시가 필요하면 별도 요구로 등재함
- **표시 규칙(프론트)** : 도달한 단계를 큐에 담아 각 **350ms 최소 표시** 후 다음으로 넘기고, 큐가 마르면 답변 텍스트로 교체함. 중단·오류·절단에서는 큐를 즉시 버림(잔류 0). 목업은 단계가 같은 순간에 도착해 이 장치 없이는 표시 시간이 0임(연출이 아니라 가독 시간 확보, P-10)
- **전송 규칙** : 단계는 라벨 문자열만 보냄(수치 미포함, P-10) · 단조 진행이라 되돌아가지 않음 · 첫 `token` 이후에는 `stage`를 보내지 않음(재검색 라운드도 드롭) · 갱신이 없으면 마지막 라벨을 그대로 유지하고 추가 연출을 만들지 않음 · 프론트는 모르는 단계 키를 무시함(리스크 R-14)
- **목업 단계의 성격** : `APP_MODE=mock`의 단계는 목 응답의 일부임(P-2 범위). 라이브 전용 단계를 목업이 따라 하지 않고, 목업이 실제로 지나는 코드 경계에서만 발생시키며, 라벨도 목업 전용 문구를 씀(P-10 · 목업 코퍼스 매칭은 사용자 문자열 키워드 비교라 문서 검색이 아님)
