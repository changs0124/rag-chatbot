## 2. 기능 상세

### FEAT-CHAT-001: 전송 전 첨부 카드 (썸네일 · 즉시 업로드)

**개요:** 파일을 고르면 입력창 위에 정사각 썸네일 카드가 뜨고, **그 즉시 서버 업로드가 시작**된다.
카드는 업로드 중 · 완료 · 실패 상태를 그대로 보여준다.

**화면:** SCR-CHAT-001 (`/`) — 입력창 영역(`frontend/src/components/chat/Composer.tsx`)

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| file | File | Y | 파일 선택기 · 카메라 촬영 · 드롭 · 붙여넣기로 들어온 원본 |
| file.type | string | Y | `image/` 로 시작하지 않으면 **받지 않는다**(조용히 버림) |

**처리 흐름:**

1. 사용자가 이미지를 고른다 (`+` 메뉴의 **사진 · 카메라** · 드롭 · 붙여넣기)
2. `URL.createObjectURL(file)` 로 로컬 미리보기 URL 을 만들어 **카드를 즉시 그린다** (네트워크를 기다리지 않는다)
3. 같은 순간 `POST /api/files` 로 업로드를 시작하고, 카드를 `uploading` 상태로 둔다
4. 성공하면 응답의 첨부 `id` 를 카드에 붙이고 `done` 으로 바꾼다
5. 실패하면 `error` 로 바꾸고 카드에 재시도 경로를 준다
6. 보내기를 누르면 **이미 올라간 첨부의 `id` 목록**으로 전송한다 (전송 시점에는 업로드가 없다)
7. 전송하면 카드 목록을 비우고 만들어 둔 미리보기 URL 을 전부 회수한다

**성공 응답:** 고른 이미지가 즉시 카드로 보이고, 업로드가 끝나면 그대로 보낼 수 있다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 업로드 중에 보내기를 누름 | **보내기 버튼을 비활성**으로 둔다. 올라가지 않은 첨부가 빠진 채 전송되는 경로를 아예 막는다 |
| 업로드 실패 (네트워크 · 413 · 400) | 카드를 `error` 로 표시하고 서버가 준 메시지를 보여준다. 재시도 또는 제거만 가능하다 |
| 실패한 카드를 둔 채 보내기를 누름 | 업로드 중일 때와 같이 **비활성**이다. 실패 카드를 화면에 두고 전송하면 그 이미지는 빠진 채 나가는데, 사용자는 카드가 보이니 갔다고 읽는다 — 재시도하거나 지워야 보낼 수 있다 |
| 업로드 **중**에 카드를 제거 | 진행 중인 요청을 `AbortController` 로 끊는다 |
| 지운 카드의 업로드가 **뒤늦게 성공** | 그 첨부를 곧바로 `DELETE /api/files/{id}` 로 지운다. 중단은 요청을 끊을 뿐 **서버가 이미 받은 것을 되돌리지 않으므로**, 여기서 지우지 않으면 회수 크론을 기다리는 고아가 된다 |
| 업로드 **완료 후** 카드를 제거 | `DELETE /api/files/{id}` 를 호출한다. 실패해도 카드는 지운다 — 남은 파일은 고아 회수가 가져간다 |
| 이미지가 아닌 파일이 들어옴 | **버린다.** 카드도 만들지 않는다 — 서버가 받지 않으므로 카드를 만들면 실패만 보여 주게 된다 |
| 전송하지 않고 화면을 떠남 | 서버에 남은 첨부는 `message_id=null` 인 고아이므로 회수 크론이 유예(`ORPHAN_TTL_MINUTES`, 기본 60분) 뒤 정리한다 |

**설계 제약 (왜 이렇게 하는가):**

- **즉시 업로드는 백엔드 변경 없이 된다.** `POST /api/files` 는 원래 `message_id=null` 로 저장하고,
  `DELETE /api/files/{id}` 가 소유자 삭제를 지원하며, 고아 회수 크론이 이미 돈다. 서버는 이 모델을 전제로 설계돼 있다.
- **미리보기는 서버 URL 이 아니라 로컬 objectURL 을 쓴다.** 업로드 왕복을 기다리면 카드가 늦게 떠서
  "고른 순간 보인다"는 느낌이 깨진다. 서명 URL 은 전송된 뒤 말풍선에서 쓴다.
- **objectURL 은 반드시 회수한다.** 회수 지점은 **카드 제거 · 전송 완료 · 컴포저 언마운트** 세 곳이다.
  회수하지 않으면 카메라로 찍고 지우기를 반복하는 동안 탭 메모리가 계속 늘어난다.
- **카드에 파일명을 쓰지 않는다.** 두 제품 모두 이미지에는 파일명을 두지 않는다.
  구분이 필요한 경우는 **카드를 눌러 확대**(FEAT-CHAT-002)로 푼다.
  다만 파일명은 접근성 정보로 남긴다 — `alt` · `aria-label` 에 넣는다.
- **문서 첨부 경로를 아예 두지 않는다.** `+` 메뉴는 사진 · 카메라 둘뿐이고, 드롭·붙여넣기로 들어온
  비이미지도 버린다. 받지 않는 것을 화면에 올려 두면 "왜 안 가지느냐"는 물음만 만든다.
- **업로드 책임이 훅에서 입력창으로 옮겨간다.** 지금은 `useChat` 이 보내기 시점에 업로드하지만,
  즉시 업로드에서는 입력창이 첨부 상태(업로드 중 · id · 오류)를 들고 있어야 한다.
  `onSend` 는 `File[]` 이 아니라 **업로드가 끝난 첨부 목록**을 넘긴다.

### FEAT-CHAT-002: 첨부 이미지 확대 보기 (좌우 이동 · 내려받기)

**개요:** 첨부 이미지를 누르면 원본을 화면 가운데 확대해 보여준다. **전송 전 카드와 전송 후 말풍선 썸네일 모두** 대상이며,
한 묶음에 여러 장이면 좌우로 넘긴다.

**화면:** SCR-CHAT-001 (`/`) — 입력창·메시지 목록 위에 뜨는 모달

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| items | `{ src, name }[]` | Y | 같은 묶음의 이미지 목록. 전송 전이면 카드 목록, 전송 후면 그 말풍선의 첨부 목록 |
| index | number | Y | 처음 열 이미지의 위치 |

**처리 흐름:**

1. 사용자가 첨부 카드 또는 말풍선 썸네일을 누른다
2. 그 묶음과 위치로 모달을 열어 화면에 맞춰(잘라내지 않고) 표시한다
3. 묶음이 2장 이상이면 좌우 버튼과 ←/→ 키로 넘긴다. **양 끝에서 순환하지 않는다**
4. 두 손가락으로 벌리면 최대 4배까지 확대하고, 확대 상태에서 끌면 이미지가 따라 움직인다.
   더블클릭(더블탭)은 1배 ↔ 2배를 오간다. **1배 아래로는 줄지 않는다** — 화면 가운데 점처럼 남으면 되돌릴 길이 안 보인다
5. 내려받기 버튼을 누르면 그 이미지를 파일로 저장한다
6. Esc · 배경 클릭 · 닫기 버튼 중 하나로 닫는다
7. 닫으면 채팅 화면은 스크롤 위치를 포함해 그대로 남는다

**성공 응답:** 원본이 화면 크기에 맞춰 표시되고, 닫으면 원래 화면으로 돌아온다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 업로드 중인 카드를 누름 | 로컬 objectURL 로 확대한다. 업로드 완료 여부와 무관하다 |
| 확대한 채로 이미지를 넘김 | 배율·위치를 초기화한다. 들고 가면 다음 장이 엉뚱한 곳에서 잘려 보인다 |
| 묶음이 1장뿐 | 좌우 버튼을 그리지 않는다 |
| 양 끝에서 더 넘김 | 아무 일도 일어나지 않는다 (순환 없음) |
| 서명 URL 이 만료됨 (TTL 15분) | 이번 범위에서 고치지 않는다. 백로그 「파일 URL 수명」과 **같은 원인**이라 함께 고치면 원인이 다른 변경이 한 커밋에 섞인다 |
| 내려받기 실패 (만료 · 네트워크) | 저장하지 않고 조용히 끝낸다. 모달은 닫지 않는다 |
| 스트리밍 중 클릭 | 스트림에 영향을 주지 않는다. 모달은 표시 계층에만 관여한다 |
| 첨부가 문서(`fileType: document`)인 과거 메시지 | 지금처럼 `📄 문서` 칩으로 두고 확대 대상에서 제외한다 |

**설계 제약 (왜 이렇게 하는가):**

- **새 모달 패턴을 만들지 않는다.** 키 처리·배경 클릭·`role="dialog"` · `aria-modal="true"` 는
  `frontend/src/components/ConfirmModal.tsx` 패턴을 그대로 따른다.
- **내려받기는 `<a download>` 만으로 안 된다.** 백엔드가 다른 오리진이라 브라우저가 `download` 를 무시하고
  새 탭으로 열어 버린다. 이미지를 `fetch` 로 받아 `Blob` objectURL 을 만들어 저장하고, 저장 후 회수한다.
- **이미지를 미리 다시 요청하지 않는다.** 확대에 쓰는 URL 은 화면에 이미 뜬 것과 같아 캐시에 있다.

### FEAT-CHAT-003: 드래그앤드롭 · 붙여넣기 첨부

**개요:** 채팅 화면에 이미지를 끌어다 놓거나, 입력창에 이미지를 붙여넣어 첨부한다.

**화면:** SCR-CHAT-001 (`/`) — 채팅 영역 전체(드롭) · 입력창(붙여넣기)

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| DataTransfer.files | FileList | Y | 드롭된 파일. 이미지가 아닌 항목은 FEAT-CHAT-001 규칙대로 버린다 |
| ClipboardEvent.clipboardData.files | FileList | Y | 붙여넣은 파일. 캡처 이미지는 파일명이 없거나 `image.png` 로 온다 |

**처리 흐름:**

1. 파일을 채팅 영역 위로 끌면 **"여기에 놓아 첨부" 오버레이**를 덮는다
2. 놓으면 FEAT-CHAT-001 의 2번 이후 흐름(카드 생성 + 즉시 업로드)을 그대로 탄다
3. 입력창에 붙여넣기(Ctrl/Cmd+V) 했을 때 클립보드에 파일이 있으면 같은 흐름을 탄다
4. 클립보드에 텍스트만 있으면 **평소대로 텍스트가 입력**된다 (기본 동작을 막지 않는다)

**성공 응답:** 끌어다 놓거나 붙여넣은 이미지가 파일 선택기로 고른 것과 똑같이 카드로 올라간다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 파일이 아닌 것(선택 텍스트·링크)을 드롭 | 오버레이를 띄우지 않고 무시한다 |
| 이미지와 텍스트가 함께 붙여넣기됨 | 파일은 첨부로, 텍스트는 입력으로 각각 처리한다 |
| 드래그가 화면 밖으로 나감 | 오버레이를 걷는다. **드래그 진입/이탈 카운터로 판정**한다 — 자식 요소를 지날 때마다 오는 `dragleave` 로 걷으면 오버레이가 깜빡인다 |
| 브라우저 기본 동작(파일을 새 탭으로 엶) | 드롭 대상에서 `preventDefault` 로 막는다. 막지 않으면 이미지가 탭을 덮어써 대화가 사라진 것처럼 보인다 |

### FEAT-ADMIN-001: 관리자 권한(role)

**개요:** `users` 테이블에 `role` 컬럼을 두고, 환경변수 `ADMIN_EMAILS` 명단에 있는 계정을 기동 시
`admin` 으로 승격한다. 결정 근거와 대안 비교는 `docs/02_architecture/backend.md` 「인증」에 있다.

**화면:** 없음 (서버 전용). 결과는 SCR-MY-001의 관리 메뉴 노출로 드러난다.

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| `ADMIN_EMAILS` | string | N | 콤마 구분 이메일 목록. 미설정이면 관리자 0명 |

**처리 흐름:**

1. 기동 시 `ADMIN_EMAILS` 를 콤마로 분리하고 각 항목을 **소문자로 정규화**한다 (기존 이메일 정규화와 같은 눈금)
2. 명단에 있는 계정을 `role='admin'` 으로 올린다
3. **명단에서 빠진 계정은 `role='user'` 로 내린다**
4. 명단에 있는데 계정이 없으면 **계정째로 만들고** 임시 비밀번호를 기동 로그에 한 번 찍는다. 이미 있으면 비밀번호를 건드리지 않는다

**성공 응답:** 없음(기동 부수효과). `GET /api/auth/me` 응답에 `role` 이 실려 프론트가 메뉴 노출을 판단한다.

**역할을 JWT에 담지 않는다.** 담으면 강등이 토큰 만료까지 반영되지 않는다. 인증 필터가 이미 요청마다
사용자 행을 읽으므로(비밀번호 변경 시각 대조) 같은 조회에서 역할을 함께 읽는다 — 추가 쿼리가 없다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| `ADMIN_EMAILS` 미설정 | 관리자 0명. 기동 정상. 관리 화면에 아무도 못 들어간다 |
| 명단에 없는 계정이 관리자 API 호출 | **404** (403 아님, P-3) |
| 대소문자가 다른 이메일 | 정규화 후 비교하므로 승격된다 |

**감수하는 약점:** 명단 변경에 재기동이 필요하다. 사내 소규모에서 관리자 교체는 드물어 감수한다.

### FEAT-ADMIN-002: RAG 문서 업로드 · 목록 · 삭제

**개요:** 관리자가 화면에서 문서를 올리면 백엔드가 OpenAI Files에 업로드하고 공용 Vector Store에
연결한다. 목록에 인덱싱 상태가 함께 뜬다.

**화면:** SCR-ADMIN-001 (`/admin`)

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| file | File | Y | PDF · TXT · MD · DOCX · 최대 25MB · PDF는 매직바이트(`%PDF`) 검사 |

**허용 형식이 채팅 첨부와 반대다.** 채팅 첨부는 비전 입력용이라 이미지만 받고, 여기는 RAG 색인용이라
문서만 받는다. 두 목록이 서로 새면 안 된다.

**25MB로 잡은 이유** : OpenAI 파일 상한(512MB)보다 훨씬 낮게 둔다. 상한에 맞추면 요청 하나가
멀티파트 버퍼를 512MB 잡아 단일 인스턴스가 그대로 멎는다. 필요해지면 스트리밍 업로드로 바꾼 뒤 올린다.

**두 한도가 겹치는 순서가 중요하다.** 코드 상한(25MB)은 `application.yml` 의 멀티파트 하드 한도(26MB)
**보다 낮아야** 한다. 같거나 높으면 멀티파트가 먼저 걷어차 코드 검사가 도달 불가능한 분기가 되고,
사용자는 무엇이 문제인지 밝히는 400 대신 413 만 받는다. 종전에는 코드가 50MB, 멀티파트가 25MB라
25~50MB 구간이 통째로 죽어 있었고 **화면은 50MB라고 안내했다**(#35). 이미지 경로는 10MB(코드) <
26MB(멀티파트)로 처음부터 이 순서를 지키고 있었다.

**매직바이트는 PDF만 검사한다.** txt·md는 매직바이트가 없고 docx는 zip 컨테이너라 `PK` 만으로는
다른 zip과 구분되지 않는다. **검사할 수 없는 형식을 검사하는 척하지 않는다.**

**형식 판정은 content-type이 1차, 파일 확장자가 2차다.** 브라우저는 `File.type` 을 OS의 MIME
레지스트리에서 채우므로, 등록이 없으면 값이 비고 `application/octet-stream` 으로 온다 — Windows의
`.md`, Office가 없는 환경의 `.docx` 가 여기 해당한다. 그때만 파일명의 확장자를 보고 허용 목록과
대조한다. **형식을 아는데 목록에 없으면(예: `image/png`) 확장자를 보지 않는다** — 그것까지 봐 주면
파일명만 바꿔 낸 파일이 통과해 검사가 사실상 해제된다. 확장자로 형식을 정한 뒤에도 PDF 매직바이트
검사는 그대로 돈다.

**처리 흐름 — 업로드:**

1. 관리자 권한을 확인한다 (아니면 404)
2. 형식·크기·매직바이트를 검사한다 (실패 400)
3. OpenAI Files에 업로드한다 → `file_id` 획득
4. 공용 Vector Store에 연결한다
5. `rag_documents` 에 `status='in_progress'` 로 기록한다

**처리 흐름 — 목록:**

1. `deleted_at is null` 인 행을 최신순으로 읽는다
2. **`status='in_progress'` 인 행에 대해서만** OpenAI에 현재 상태를 조회해 갱신한다.
   완료·실패는 더 바뀌지 않으므로 전 행을 매번 조회하지 않는다

**처리 흐름 — 삭제:**

1. 관리자 권한 확인
2. Vector Store 연결 해제 → OpenAI 파일 삭제
3. `deleted_at` 을 채운다 (soft delete)

**성공 응답:** 업로드 `201` + 문서 DTO · 목록 `200` + 배열 · 삭제 `204`

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 비관리자 접근 | `404` (P-3) |
| 미인증 | `401` |
| 허용하지 않는 형식 | `400` — 메시지에 허용 목록을 적는다 |
| 크기 초과 | `400` |
| `OPENAI_VECTOR_STORE_ID` 미설정 | `400` "스토어가 설정되지 않아 업로드할 수 없음". **행을 만들지 않는다** — 조용히 성공시키면 어디에도 없는 문서가 목록에만 뜬다 |
| 3단계(Files 업로드) 실패 | 아무것도 안 남는다. `500` |
| 4단계(스토어 연결) 실패 | OpenAI에 고아 파일이 남는다. 즉시 파일 삭제를 시도하고 실패 시 경고 로그. **행은 만들지 않는다** |
| 5단계(DB 기록) 실패 | 스토어에는 들어갔는데 기록이 없는 상태로 **가장 나빴던 자리다.** 지금은 파일과 스토어 연결을 즉시 되돌리고(#72) 실패 시 경고 로그에 `file_id` 를 남긴다 — 4단계와 같은 방식이다. **되돌리기까지 실패하면 여전히 남는다**(`deleteQuietly` 라 조용히 실패한다). `OrphanCleanupScheduler` 는 로컬 첨부만 회수하므로 그 잔여분은 로그로만 찾을 수 있다 |
| 5단계 성공 **직후 재조회** 실패 | `upload()` 는 넣은 행을 목록에서 다시 찾아 응답을 만든다. 못 찾으면 `IllegalStateException` → `500` 인데 **`@Transactional` 이 없어 행은 이미 커밋돼 있다.** 관리자는 실패로 읽지만 목록에는 문서가 있다 — 위 5단계 실패와 정반대로 **행이 남는 쪽**의 어긋남이다 |
| 삭제 시 OpenAI 정리 실패 | `deleted_at` 은 그대로 채운다. 목록에 남겨두면 이미 검색에서 빠졌을 수 있어 상태가 더 헷갈린다. 고아는 별도 정리 |

**목업 모드** : `APP_MODE=mock` 에서도 전 경로가 동작한다(P-2). OpenAI 호출 없이 메모리에 파일 ID를
만들고 상태를 곧바로 `completed` 로 둔다. 목업임이 드러나도록 ID에 `mock-` 접두를 붙인다.

**soft delete 를 쓰는 이유** : "언제 내려갔는가"가 감사 대상이다(REQ-ADMIN-002). 행을 지우면 그 사실이
남지 않는다. 이 저장소의 다른 테이블은 대부분 hard delete + cascade 이며, 여기만 다른 것은 의도다.

### FEAT-ADMIN-003: 관리자에 의한 비밀번호 초기화

**개요:** 관리자가 사용자 목록에서 임시 비밀번호를 발급한다. 이메일 발송 수단(SMTP)을 도입하지 않고
REQ-AUTH-006을 충족시키기 위한 선택이다.

**화면:** SCR-ADMIN-002 (`/admin` 내 사용자 섹션)

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| userId | uuid (경로) | Y | 존재하는 사용자. **자기 자신은 대상에서 제외** |

**처리 흐름:**

1. 관리자 권한 확인
2. `SecureRandom` 으로 임시 비밀번호를 생성한다
3. 해시로 저장하면서 **`password_changed_at` 을 함께 올린다** — 기존 무효화 기준선 규칙을 그대로 탄다.
   초기화 즉시 그 사용자의 **모든 기존 토큰이 무효**가 된다
4. 평문 임시 비밀번호를 **응답에 한 번만** 담아 돌려준다. 저장하지 않는다

**성공 응답:** `200` + 임시 비밀번호 1회. 화면은 "다시 볼 수 없음"과 "대상자가 즉시 로그아웃됨"을 함께 알린다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 비관리자 호출 | `404` |
| 없는 사용자 | `404` |
| 자기 자신 대상 | 화면에 버튼을 띄우지 않는다. 마이페이지에 비밀번호 변경이 이미 있다 |

**감수하는 약점** : 임시 비밀번호 전달 경로가 제품 밖(사내 메신저 등)이라 그 구간은 보증되지 않는다.
이메일 인증을 도입하면 이 기능은 대체된다.

**최초 로그인 시 변경 강제는 범위 밖이다.** 별도 상태 컬럼과 화면 분기가 필요해 범위가 커지고,
사내 소규모에서는 관리자 구두 안내로 충분하다.

### FEAT-OPS-001: 턴별 토큰 사용량 기록

**개요:** OpenAI 완료 이벤트에 실려 오는 `usage` 를 읽어 어시스턴트 메시지에 함께 저장한다.
지금은 인용만 뽑고 나머지를 버리므로, **새로 호출하는 것이 아니라 버리던 것을 줍는다** — 추가 API 비용이 0이다.

**화면:** 없음. 이번 범위는 **기록까지**다. 집계 화면은 데이터가 쌓인 뒤 무엇을 볼지 정해지면 만든다.

**입력값:** 없음 (응답 파싱)

**처리 흐름:**

1. `response.completed` 에서 `usage.input_tokens` · `usage.output_tokens` 를 읽는다
2. 없으면 `null` 로 둔다. **0으로 만들지 않는다**
3. 어시스턴트 메시지 저장 시 함께 넣는다

**성공 응답:** 없음(저장 부수효과). 조회는 `docs/01_specs/erd.md` 의 사용량 조회 SQL 참고.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| `usage` 필드 없음 | `null`. 추정해서 채우지 않는다 |
| 중단·오류로 부분 저장 | `null`. 비용은 발생했지만 값을 알 방법이 없다 |
| 목업 모드 | `null`. 숫자를 지어내면 합계가 거짓이 된다 |

**nullable 로 두는 이유** : `0` 을 기본값으로 두면 **"모르는 것"과 "정말 0"이 구분되지 않는다.**
`stopped` 컬럼(V3)과 같은 판단이며, 이전 행을 소급 보정하지 않는다.

### FEAT-OPS-002: 예외 최종 폴백 + 요청 상관 ID

**개요:** `GlobalExceptionHandler` 에 `Exception` 핸들러를 더해, 예상하지 못한 예외도
`ApiError{code, message}` 형태로 나가고 서버 로그에 남게 한다.

**화면:** 없음 (오류 문구만 바뀐다)

**지금 무슨 일이 일어나는가:**

| 단계 | 현재 |
|------|------|
| 예외 발생 | 도메인 예외가 아니면 핸들러에 걸리지 않는다 |
| 응답 | Spring 기본 형태(`timestamp` · `status` · `error` · `path`)로 나간다 |
| 프론트 | `data?.message` 를 찾다 실패해 `요청 실패 (500)` 만 띄운다 |
| 서버 로그 | **어느 요청이었는지 상관 지을 기록이 없다** |

**처리 흐름:**

1. 요청마다 짧은 상관 ID를 만든다 (8자리. UUID 전체는 사용자에게 읽히기 부담스럽다)
2. 예외를 **스택트레이스와 함께** `ERROR` 로 남긴다. 상관 ID · 메서드 · 경로를 함께 적는다
3. 응답은 `{"code":"INTERNAL_ERROR","message":"처리 중 오류가 발생했습니다 (오류 번호: a1b2c3d4)"}`

**성공 응답:** 해당 없음

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 도메인 예외(400/404/409/429 등) | **폴백에 걸리지 않는다.** 기존 핸들러가 그대로 처리 |
| SSE 스트림 도중 오류 | 대상 아님. 응답이 이미 시작돼 손댈 수 없고, `ChatService` 가 `event: error` 로 이미 처리한다 |
| 예외 메시지에 내부 정보 | **응답에 싣지 않는다.** SQL 조각·클래스 이름이 나가면 정보 노출이다 |

**상관 ID를 두는 이유** : 사용자가 "오류가 났어요"라고 말할 때 지금은 서버 로그에서 그 순간을 찾을
방법이 없다. 번호 하나면 바로 찾힌다. 관측 도구 없이 얻을 수 있는 가장 큰 몫이다.

### FEAT-OPS-003: 세션 슬라이딩 재발급

**개요:** 만료가 가까운 토큰으로 요청이 들어오면 응답 헤더에 새 토큰을 실어 보낸다.
활동 중이면 만료가 계속 밀린다. 대안 비교를 아래에 남긴다.

| 안 | 채택 | 사유 |
|----|------|------|
| 슬라이딩 재발급 | **채택** | 새 테이블이 없고 기존 `password_changed_at` 무효화 규칙과 그대로 호환된다 |
| 리프레시 토큰 | 기각 | 테이블 · 회전 · 재사용 탐지까지 붙어 작업량이 3~4배다 |
| 만료 시간만 연장 | 기각 | 탈취된 토큰의 유효 기간도 같이 늘어난다 |

**화면:** 없음 (사용자에게 보이지 않는다)

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| `JWT_REFRESH_THRESHOLD_MINUTES` | int | N | 기본 30. **`0` 이면 기능을 끈다**(종전 고정 만료로 되돌리는 경로) |

**처리 흐름:**

1. JWT 검증 성공 후, 남은 수명이 임계 미만이면 새 토큰을 발급한다
2. 응답 헤더 `X-Refresh-Token` 에 싣는다
3. 프론트 `frontend/src/lib/api.ts` 의 fetch 래퍼가 헤더를 보면 `setToken()` 으로 교체한다
4. **채팅 스트림 경로도 같이 처리한다** — `frontend/src/lib/endpoints.ts` 가 래퍼를 거치지 않고
   직접 `fetch` 하므로, 한쪽만 하면 채팅만 쓰는 사용자는 갱신을 못 받는다

**성공 응답:** 헤더만 추가된다. 본문은 그대로다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| CORS 노출 헤더 미등록 | **서버는 정상 발급하는데 브라우저가 못 읽어 조용히 아무 일도 안 일어난다.** `CorsConfig` 에 `X-Refresh-Token` 을 노출 헤더로 등록해야 한다 |
| 30분 넘게 요청 없음 | 그대로 만료된다. 배경 갱신 타이머를 두지 않는다 — 아무도 안 쓰는 탭이 세션을 영구히 살려두는 편이 더 나쁘다 |

**임계를 두는 이유** : 매 요청 재발급하면 서명 연산이 요청마다 붙고 헤더가 늘 커진다.
만료가 가까울 때만 하면 실제 발급은 사용자당 30분에 한 번꼴이다.

### FEAT-AUTH-001: 관리자 계정 발급 + 이메일 도메인 화이트리스트

**개요:** 스스로 가입하는 경로가 없다. 관리자가 `POST /api/admin/users` 로 계정을 만들어 임시
비밀번호를 전달하고, 받은 사람이 그것으로 로그인한다. 도메인 화이트리스트는 **발급 시점에** 걸린다.

**2026-08-19 의 결정을 뒤집었다**(2026-09-07). 당시 표는 이렇게 적혀 있었다.

| 안 | 당시 판단 | 사유 |
|----|------|------|
| 도메인 화이트리스트 | 채택 | 사내 도메인 메일을 가진 사람은 어차피 승인될 사람이다. `ADMIN_EMAILS` 와 같은 env 명단 패턴이 이미 있어 새 개념이 늘지 않는다 |
| 관리자 승인 대기 | 기각 | `users.status` 신설 + 승인 화면이 필요한데, 관리자가 매번 개입해야 하는 값에 비해 비싸다 |
| **가입 자체를 닫기** | **기각** | 관리자가 계정을 일일이 발급해야 한다. 사람이 늘 때마다 운영 부담이 선형으로 는다 |

**무엇이 바뀌어 판단이 뒤집혔나.** 기각 사유였던 "일일이 발급"의 비용이 그 사이 크게 줄었다 —
FEAT-ADMIN-003 이 임시 비밀번호 생성·1회 반환·기존 토큰 무효화를 이미 갖췄고, 관리 화면에도
사용자 목록이 이미 있었다. 발급에 새로 필요했던 것은 **폼 하나와 엔드포인트 하나**였다.
반대편에서는 도메인 제한만으로 부족하다는 것이 드러났다 — 같은 도메인 안이면 누구든, 퇴사자를
포함해, 여전히 스스로 계정을 만들 수 있었다.

도메인 화이트리스트는 **없애지 않았다.** 관리자가 주소를 손으로 치므로 오타 한 번이면 사외 주소에
계정이 열린다. 경계가 서는 자리만 가입에서 발급으로 옮겼다.

**대가로 생긴 것** : 빈 DB 에서 첫 관리자를 만들 길이 사라졌다. 종전에는 관리자도 스스로 가입해
태어났기 때문이다. 그래서 기동 러너가 `ADMIN_EMAILS` 를 보고 **계정째로 만든다**(FEAT-ADMIN-001).

**화면:** 로그인 화면에서 회원가입 토글이 사라지고 「계정은 관리자가 발급합니다」 안내가 그 자리에
들어간다. 진입점만 지우면 사용자는 어디로 가야 할지 모른 채 멈춘다.
관리 화면 사용자 구역에는 **계정 추가 폼**이 생긴다 — 임시 비밀번호는 초기화와 같은 모달로 1회 보여준다.

**입력값:**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|------|---------|
| `ALLOWED_EMAIL_DOMAINS` | string | 조건부 | 콤마 구분 도메인 목록. `@` 없이 도메인만(`company.com`) |

**`APP_MODE=live` 에서만 필수다.** 비어 있으면 **기동을 막는다** — `OPENAI_API_KEY` 와 같은 fail-fast
패턴이다. `mock` 에서는 비어도 되고 그때는 전원 허용이다.

이렇게 가르는 이유 : "비면 전원 허용"으로 두면 배포에서 변수를 빠뜨렸을 때 **조용히 경계가 사라지는데**
아무도 모른다. 반대로 mock 까지 필수로 두면 개발·테스트가 전부 막힌다(통합 테스트가 매 케이스
계정을 만든다).

**처리 흐름:**

1. 기동 시 명단을 콤마로 분리하고 소문자로 정규화한다. `live` 인데 비어 있으면 기동 실패
2. 발급 요청의 이메일을 소문자로 정규화한다(기존 규칙)
3. `@` 뒤를 잘라 명단과 **정확히 일치**하는지 본다
4. 일치하지 않으면 `400` 으로 거절한다. **중복 검사보다 먼저** 한다 — 거절할 주소에 대해
   "이미 있는 이메일"을 돌려주면 계정 존재 여부가 새어 나간다
5. 통과하면 임시 비밀번호를 만들어 계정을 넣고, 그 값을 **응답에 한 번만** 싣는다.
   역할은 `ADMIN_EMAILS` 명단에 있을 때만 `admin` 이다 — 발급하는 쪽이 관리자라는 이유로
   받는 쪽까지 관리자가 되면 계정 하나 만들 때마다 권한이 번진다

**성공 응답:** `201` + `{ "temporaryPassword": "…" }`. 비밀번호 초기화와 같은 형태다.

**서브도메인은 포함하지 않는다.** `company.com` 을 허용해도 `mail.company.com` 은 막힌다.
접미사 매칭으로 두면 `evil-company.com` 같은 주소가 통과하는 실수를 부르기 쉽다.
서브도메인이 필요하면 명단에 따로 적는다.

**`ADMIN_EMAILS` 는 도메인 검사를 면제한다.** 관리자 이메일이 허용 도메인 밖이면 **관리자를 만들 수
없어 부트스트랩이 막힌다.** 명단 자체가 배포 설정이라 이미 통제되어 있으므로 면제해도 공격면이 늘지 않는다.

**예외 처리:**

| 상황 | 처리 방식 |
|------|---------|
| 허용 도메인 밖 | `400` — 메시지에 **허용 도메인을 밝힌다**. 사내 도메인은 비밀이 아니고, 숨기면 "왜 안 되는지 모르겠다"는 문의만 는다 |
| `@` 가 없는 값 | `@Email` 검증이 먼저 걸러 `400` |
| `live` 인데 명단 미설정 | **기동 실패.** per-request 로 흘리지 않는다 |
| `mock` 이고 명단 미설정 | 전원 허용(종전 동작) |
| 관리자 명단에 있는 주소 | 도메인과 무관하게 허용 |

**감수하는 약점 1 — 임시 비밀번호 전달 구간이 제품 밖이다.** 관리자가 사내 메신저 등으로 옮기며,
그 구간은 보증되지 않는다. FEAT-ADMIN-003 이 이미 안고 있던 약점과 같은 것이다.

**감수하는 약점 2 — 첫 관리자의 임시 비밀번호가 기동 로그에 남는다.** 로그 수집기를 붙이면 그쪽으로도
간다. 환경변수로 받는 안은 값을 바꾸지 않는 한 계속 유효한 비밀번호로 남아 더 나빴고, 마이그레이션
시드는 해시가 저장소에 박혀 모든 배포가 같은 초기 비밀번호를 갖게 되어 더 나빴다.

**감수하는 약점 3 — 이미 있는 도메인 밖 계정은 그대로 남는다.** 검사는 **계정을 만드는 시점에만** 한다.
로그인에서도 막으면 정책 도입 이전에 정당하게 만들어진 계정이 통째로 잠긴다. 그런 계정을 실제로
치우려면 계정 삭제 기능이 필요한데 지금 없다 — 별개 문제로 남긴다.
