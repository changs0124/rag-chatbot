> **이 문서의 목적** — API 키와 공용 Vector Store가 확보됐을 때 **무엇을 어떤 순서로 꽂고,
> 무엇을 확인하면 "동작한다"고 말할 수 있는지**를 정한다. 키 · 스토어 · 모델을 바꿀 때 다시 밟는 **절차**와
> 어긋났을 때 보는 **진단표**(3절)다.

**밖에서 먼저 만들어 와야 하는 것 둘**

| 준비물 | 만드는 곳 | 형태 |
|--------|-----------|------|
| API 키 | OpenAI 플랫폼 → **API keys** | `sk-` 로 시작. 발급 직후 한 번만 보이므로 그 자리에서 옮겨 적는다 |
| Vector Store | OpenAI 플랫폼 → **Storage → Vector stores** | ID 가 `vs_` 로 시작. **비워서 만든다** — 문서는 2-3 에서 제품 화면으로 넣는다(이유는 [5절](#5-문서를-넣는-경로)) |

키가 살아 있는지는 한 줄로 확인된다. 스토어 목록이 200 으로 돌아오면 키와 권한이 정상이다.

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://api.openai.com/v1/vector_stores \
  -H "Authorization: Bearer $OPENAI_API_KEY"
```

200 이면 2-1 로 넘어가고, 401 이면 키를, 403 이면 프로젝트 권한을 본다. `OpenAI-Beta: assistants=v2` 헤더는
필수가 아니다(#37, 2026-09-22 판정 — 쓰기 경로까지 헤더 없이 200). 코드는 공식 SDK 와 맞춰 그대로 싣고, 부착 범위는
`OpenAiRealBetaHeaderTest` 가 잠근다.

**함께 볼 문서** — 배포 절차는 [`docs/02_architecture/backend.md`](../02_architecture/backend.md) 「배포」,
관리자 업로드 기능 명세는 [`docs/01_specs/features.md`](./features.md) FEAT-ADMIN-002,
환경변수 전량과 빠뜨렸을 때의 증상은 `backend/.env.example` 에 있다.

## 0. 현재 상태

실 응답 검증(2026-09-22, #184)과 운영 투입(2026-10-06)은 끝났다 — 경위는 [CHANGELOG](../06_changelog/CHANGELOG.md).
지금 운영 모델은 `OPENAI_MODEL` 기본값(#277)이고, 키 · 스토어 ID 는 운영 서버 `backend/.env` 에만 있다.

## 1. 준비물

환경변수 전량과 각 값의 뜻 · 형식은 `backend/.env.example` 이 정본이다. 값은 저장소에 넣지 않는다.
여기서는 **투입 관점** — 빠뜨린 것이 언제 드러나는가 — 만 적는다.

**기동을 막는 것** — `APP_MODE` · `JWT_SECRET`(32바이트 미만 포함) · `DB_URL`(+ `DB_USERNAME` · `DB_PASSWORD`) ·
`OPENAI_API_KEY`(live) · `ALLOWED_EMAIL_DOMAINS`(live). 하나라도 비면 컨텍스트가 뜨지 않으므로 **기동에 성공했다는
사실 자체가 이들이 들어갔다는 근거**가 된다.

나머지는 기동은 되고 **나중에 증상으로 드러나므로** 더 찾기 어렵다 :

| 빠뜨린 것 | 드러나는 시점 | 증상 |
|-----------|--------------|------|
| `OPENAI_VECTOR_STORE_ID` | 2-3 | 업로드가 400 `Vector Store 가 설정되지 않아 업로드할 수 없음` 으로 거부된다. 업로드를 건너뛰어도 `file_search` 툴이 아예 안 붙어 **출처가 늘 0건**이 된다 |
| `ADMIN_EMAILS` | 2-3 | 관리자가 0명이라 **로그인할 계정 자체가 없다.** 스스로 가입하는 경로가 없어 되돌릴 방법이 재기동뿐이다 |
| `OPENAI_MODEL` (비전 미지원으로 바꾼 경우) | 2-6 | 이미지 첨부만 답변이 어긋난다. 비전 입력을 쓰므로 **이미지 지원 모델이어야 한다** |
| `APP_DB_USER` · `APP_DB_PASSWORD` (루트 `.env`, #415) | 기동 | 비우면 기동은 되지만 **앱이 슈퍼유저로 접속한다**(옛 구성). 계정을 만들지 않고 값만 넣으면 기동이 `password authentication failed` 로 멈춘다 — 계정 생성은 backend.md 「런타임 DB 계정」 |
| `DOC_FIGURES_DIR` (또는 그 폴더를 비워 둠) | 5-1 | 답변에 그림 표식이 들어가도 **그림 자리가 비고 텍스트만 보인다.** 오류가 나지 않아 고장으로 보이지 않는다 |

**`ADMIN_EMAILS` 의 주소는 `ALLOWED_EMAIL_DOMAINS` 밖이어도 된다.** 도메인 검사를 면제받으므로
관리자 이메일이 사내 도메인이 아니어도 부트스트랩이 막히지 않는다.

### 1-1. 값을 어떻게 넣는가

**`backend/.env` 는 저절로 읽히지 않는다.** 저장소에 dotenv 로더가 없고(`backend/pom.xml`)
`spring.config.import` 도 걸려 있지 않다. 그 파일을 실제로 소비하는 곳은 `docker-compose.yml` 의
`env_file` **한 곳뿐**이다. 이것을 모르면 `.env` 를 정성껏 채우고도 `APP_MODE 미설정` 으로 기동에 실패하고,
방금 값을 적어 넣은 사람에게 그 메시지는 원인을 가리키지 않는다.

| 띄우는 방법 | 값이 들어가는 경로 |
|-------------|--------------------|
| **`docker compose` (권장)** | `backend/.env` 를 `env_file` 로 읽는다. DB 접속 셋은 compose 가 덮어쓰므로 루트 `.env` 의 `POSTGRES_PASSWORD` 하나만 맞추면 된다. 절차는 [`backend.md` 「배포」](../02_architecture/backend.md) |
| `./mvnw spring-boot:run` | **`.env` 를 읽지 않는다.** 셸에 직접 넣어야 한다 — `export $(grep -v '^#' backend/.env \| xargs)` 또는 변수를 하나씩 `export` |

권장은 compose 다. DB 컨테이너가 함께 뜨므로 위 표의 `DB_*` 를 따로 준비할 필요가 없고,
실 배포와 같은 경로를 밟게 되어 "로컬에서는 됐는데" 가 줄어든다.

## 2. 투입 절차

각 단계는 **다음 단계로 넘어가기 전에 확인할 것**을 함께 적는다. 확인 없이 다음으로 넘어가면
실패했을 때 어느 단계가 원인인지 분리되지 않는다.

> **순서를 지켜야 하는 이유** — 문서를 넣는 유일한 경로가 제품 화면인데(5절), 그 경로는
> `OPENAI_VECTOR_STORE_ID` 가 이미 주입돼 **기동한 뒤에만** 열린다(`AdminDocumentService.upload` 의 첫 가드).
> 그래서 스토어를 만드는 것과 문서를 넣는 것이 붙어 있지 않고, 사이에 기동이 들어간다.
> 대시보드에서 문서까지 올려 두면 순서는 짧아지지만 관리 화면에서 보이지도 지워지지도 않는 상태가 된다.

### 2-1. 빈 Vector Store 를 만들고 ID 만 챙긴다

**문서는 넣지 않는다.** 스토어만 만들고 `vs_` 로 시작하는 ID 를 복사한다.

- 확인 : 위쪽 「밖에서 먼저 만들어 와야 하는 것 둘」 의 curl 이 200 을 돌려준다.

### 2-2. 환경변수를 넣고 백엔드를 `APP_MODE=live` 로 띄운다

1-1 의 방법으로 값을 주입한다. `OPENAI_VECTOR_STORE_ID` 에 2-1 의 ID 를 넣는다.

- 확인 : 기동이 성공한다(1절 「기동을 막는 것」이 다 들어갔다는 근거).
- 확인 : 기동 로그의 `관리자 명단 동기화 : 명단 N건 · 생성 N건 …` 줄을 본다. 명단 건수가 0이면
  `ADMIN_EMAILS` 를 빠뜨린 것이고, 그대로 두면 다음 단계에서 **로그인할 계정이 없다.**
- 확인 : 계정이 새로 만들어졌다면 로그에 `관리자 계정 발급 : … 임시 비밀번호 XXXX-XXXX-XXXX` 가
  **한 번만** 찍힌다. 재발급 경로가 없으므로 그 자리에서 옮겨 적는다.

**`vs_` ID 가 틀려도 기동은 성공한다.** 형식·실재를 검사하는 코드가 없어(`OpenAiRealService.hasSharedVectorStore`
는 공백 여부만 본다) 오타는 2-3 이나 2-4 에서야 드러난다. 증상과 대처는 3-1 에 있다.

### 2-3. 관리자로 로그인해 문서 1건만 올린다

처음부터 전량을 올리지 않는다. **문서 1건**이면 3절의 가정이 전부 드러난다.
경로는 `/admin/documents` 화면 또는 `POST /api/admin/documents` — 둘 다 5절의 같은 경로다.
**OpenAI 대시보드로 올리지 않는다**(이유는 5절).

- 확인 : 응답이 201 이고 `status` 가 `in_progress` 다.
- 확인 : `GET /api/admin/documents` 를 다시 불러 `status` 가 `completed` 로 바뀐다.
  `in_progress` 로 멈춰 있으면 파싱 단계에서 막힌 것이라 아래 단계가 전부 무의미하다.

### 2-4. 2-3에서 올린 문서의 내용을 묻는다

- 확인 ① : 답변 토큰이 **흘러서** 온다(한 번에 뭉쳐 오지 않는다). 뭉쳐 오면 스트리밍이 아니라
  버퍼링된 것이므로 `RestClient` 응답 처리를 봐야 한다.
- 확인 ② : 진행 단계에 **「참조 문서 검색 중」** 이 뜬다. 안 뜨면 `file_search` 호출 이벤트가
  도착하지 않은 것이다(3절 가정 A). 이어서 **「참조 문서 확인 중 · <문서명>」** 이 뜬다. 안 뜨면 3절 가정 G.
- 확인 ③ : 답변 하단에 **출처 각주가 뜬다**. 각주가 없고 「자료 없음」 배너가 뜨면 인용 추출이
  실패한 것이다(3절 가정 B·C).

### 2-5. 자료에 없는 것을 묻는다

- 확인 : 「자료 없음 - 관련 자료를 찾지 못해 추론으로 답변함」 배너가 뜬다. 2-4와 2-5가 **모두**
  기대대로 나와야 무자료 판정이 동작하는 것이다. 한쪽만 보면 "항상 0건"과 구분되지 않는다.

### 2-6. 이미지를 첨부해 묻는다

- 확인 : 이미지 내용을 반영한 답변이 온다. `OPENAI_MODEL` 을 비전 미지원 모델로 바꿨다면 여기서 드러난다.

### 2-7. 전량 업로드

2-1~2-6이 전부 통과한 뒤에 문서를 전량 올린다. 경로는 2-3과 같다. 이 시점부터는 저장 용량 과금이 시작된다.

## 3. 실 응답과 대조해야 하는 가정

아래 가정은 2026-09-22 실연동으로 A~E 가 확인됐고 F 는 틀렸지만 무해했다(#184 · #37, 관측 원본 `.issue/184/evidence/`). G 는 2026-10-19 에 따로 확인했다(#375, 표 안).
모델·API 가 바뀌어 다시 어긋날 때를 위한 진단표다 — 2-4에서 기대와 다른 결과가 나오면 여기부터 본다.

| ID | 가정 | 어긋나면 나타나는 증상 |
|----|------|------------------------|
| A | 검색 시작 이벤트 이름이 `response.file_search_call.in_progress` 또는 `response.file_search_call.searching` | 「참조 문서 검색 중」 단계가 화면에 뜨지 않는다. 답변은 정상 |
| B | 완료 이벤트 이름이 `response.completed` | **스트림이 완료 없이 끝났다**는 오류로 끝난다. 조용히 무자료로 넘어가지 않도록 일부러 던지게 해 둔 경로다. 앞서 `error` · `response.failed` 가 왔으면 그 `code` · `type` · `message` 를 오류 문구에 싣는다(#536 — 크레딧 소진은 HTTP 200 으로 열린 스트림에 이 둘로 온다, 2026-10-28 운영 키로 실측 : `insufficient_quota` / `credit_balance_exhausted`) |
| C | 인용 annotation의 타입이 `file_citation` 이고 파일명 필드가 `filename` | 답변은 정상인데 출처가 늘 0건이라 **모든 답변에 「자료 없음」 배너**가 붙는다 |
| D | 검색 결과 본문이 `file_search_call` 항목의 `results[].text` 에 실린다 | 출처 각주는 뜨는데 스니펫이 빈칸이다 |
| E | `include: ["file_search_call.results"]` 로 결과 본문을 받을 수 있다 | D와 같은 증상 |
| F | Vector Store 계열 호출에 `OpenAI-Beta: assistants=v2` 가 **필요하다** | 없음 — 헤더 없이도 200(위 「밖에서 먼저 만들어 와야 하는 것 둘」 아래) |
| G | 검색이 끝나면 `response.output_item.done` 이 `item.type=file_search_call` 과 `item.results[].filename` 을 싣는다(#375. 2026-10-19 운영 키 · 스토어로 실측 확인 : `file_search_call.completed` 뒤, 첫 `output_text.delta` 앞에 status=completed · results 20건 · filename 두 종) | 「참조 문서 확인 중 · …」 단계가 뜨지 않는다. 답변 · 출처는 정상(출처는 `response.completed` 에서 따로 읽는다) |

가정 C는 특히 **오진하기 쉽다.** "자료 없음"은 정상 동작으로도 나오는 표시라, 스토어에 문서가 있는데도
0건이면 검색이 안 된 것인지 인용 추출이 깨진 것인지 화면만 봐서는 구분되지 않는다. 2-4에서
**스토어에 확실히 있는 내용**을 물어 구분한다.

### 3-1. 증상에서 원인으로 — 어디부터 보는가

같은 화면이 여러 원인에서 나온다. 특히 **「자료 없음」 하나에 원인이 넷** 몰려 있어, 화면만 보고는
갈라지지 않는다. 아래는 증상에서 거슬러 올라가는 순서다.

| 증상 | 먼저 볼 것 | 갈라내는 방법 |
|------|-----------|--------------|
| 전 답변에 「자료 없음」 | `OPENAI_VECTOR_STORE_ID` 가 비었는지 | 비면 `file_search` 툴이 아예 안 붙는다. 2-3 업로드가 400 으로 거부됐다면 이쪽이 확실하다 |
| 〃 | `vs_` ID 오타 | 업로드가 500 으로 실패한다. 서버 로그에 `openai … 400`·`404` 가 남는다 |
| 〃 | 인용 추출(가정 C) | 업로드는 `completed` 인데 출처만 0건이면 이쪽 |
| 〃 | 모델이 검색을 건너뜀 | 위 셋이 아니면 남는 것은 이것이다. `instructions` 로 유도하되 `tool_choice` 로 강제하지는 않는다(아래 3-2) |
| 본문은 「찾지 못했다」인데 출처가 붙고 「자료 없음」이 안 뜸 | 지시문의 무인용 줄(#181) | 판정이 `citations.isEmpty()` 하나라 인용 1건이면 출처 있음이다. 모델이 「현재 자료는 A·B 뿐」 같은 부재 설명 문장에 인용을 단 것이다. 지시가 실려 나가는지는 `OpenAiRealInstructionsTest` 가 잠그므로, 재발하면 모델 쪽이다 |
| 본문은 자료를 근거로 답했는데 출처가 비고 「자료 없음」이 뜸 | 모델이 annotation 없이 답함(#281) | `gpt-6-sol`에서 간헐적으로 나온다(빈도는 CHANGELOG #281). 본문에 인용 표기는 썼는데 annotation 이 0건인 경우다. **지금은 표기로 출처를 복원한다** — 아래 「인용 표기 대응 규칙」. 그래도 뜨면 표기마저 없었거나, 표기가 검색 결과 범위 밖을 가리킨 것이다 |
| 채팅이 `"응답 생성 중 오류"` 로 끝남 | 서버 로그 | OpenAI 응답 본문은 화면에 내려가지 않는다. 단서는 `openai responses api error <코드>: {...}` 한 줄뿐이다 |
| 업로드가 `"처리 중 오류가 발생했습니다 (오류 번호: …)"` | 서버 로그 | 같은 이유로 원인이 화면에 없다. 오류 번호로 로그를 찾는다 |

**인용 표기 대응 규칙(#277 · #281)** — sol 계열은 본문에 `U+E200 filecite U+E202 turn0file2 U+E202 turn1file0 U+E201`
같은 표기를 흘린다. `CitationMarkupFilter` 가 이 표기를 화면·저장본에서 걷어 내고, 그 안의 참조는 모아 둔다.
`turnNfileM` 은 응답 `output[]` 안의 **N번째 `file_search_call` 의 `results[M]`** 이다(둘 다 0-base).
2026-10-15 실측(OpenAI 직접 호출 12회)에서 범위 밖 참조는 0건이었다. 표기와 annotation 이 함께 온 6개 답에서는
이 규칙으로 얻은 파일 집합이 annotation 과 전부 같았다. **annotation 이 0건일 때만** 이 규칙으로 출처를 채운다.
범위 밖 참조와 `filecite` 가 아닌 표기는 버린다. 한계 : 실측 당시 스토어에 파일이 2개뿐이라, 파일 단위 검증의
구분력은 약하다. 스토어 문서가 늘면 다시 잰다.
표기가 **문서 이름 자리**에 오면(앞이 「은 · 는 · 을 · 를」+ 공백 또는 붙어 쓴 「은 · 는」, 뒤 첫 글자가 쉼표나 「에 · 의 · 와 · 과 · 을 · 를」) 지우는 대신
같은 규칙으로 찾은 파일명에서 확장자(`.md` 등)를 뺀 이름을 넣는다(#429) — 지우기만 하면 「기록은  , … 기록은  에서」처럼 빈칸이 남는다.
검색 결과(`output_item.done`)가 본문보다 먼저 오므로 스트림 도중에 풀린다. 이름으로 풀리지 않는 참조와 그 밖의 위치(문장 끝 ·
표 칸 등)는 지금처럼 지우기만 한다. 「이 · 가 · 도 · 로 · 과」는 명사 끝(결과 · 온도 · 회로)이나 단어 첫 글자(이상 · 이후)로도 흔해
판정에서 뺐다 — 넣으면 「점검 결과 <표기> 이상 없음」 같은 정상 문장에 이름이 끼어든다.
필터가 내보내는 글자는 마지막에 `SourceNameRewriter` 를 거친다(#470). 모델이 어느 문서인지 글로 밝힐 때 검색 결과 파일 이름을
확장자 · 문서 코드째 옮기므로(「TM매뉴얼_VSVDTMNOPK10_v3.md의 …」, 2026-10-26 운영 QA 892턴 중 코드 17 · 확장자 3), 검색 결과
이름과 같은 글자만 **확장자를 빼고 첫 `_` 앞까지**로 바꾼다(「TM매뉴얼」 · 「필드클레임현황」). 위의 #429 가 넣는 이름도 같은 규칙을
따르고, 출처 목록(`sourceName`)은 파일 이름 그대로다. 이름이 조각 사이에서 잘려 올 수 있어 끝이 이름의 앞부분이면 다음 조각까지
붙잡는다 — 정지로 끊긴 답은 그 꼬리(이름 길이 미만)가 저장본에 남지 않는다. 첫 `_` 앞이 같은 문서가 둘 이상이면
어느 문서인지 가릴 수 없어 확장자만 뺀다. 이미 내보낸 글자는 되돌리지 못해, 겹치는 이름이 나중 검색에서 처음 오면 그 전 본문은 짧은 이름 그대로다. 지시문으로 막는 쪽은 뺐다 : 「파일 이름 대신 짧은
이름으로 부른다」 줄을 넣으면 노출은 0 이 되지만 근거로 답하고도 인용을 하나도 달지 않는 답이 배터리 124회 중 1 → 5 로 늘어
「자료 없음」이 잘못 뜬다(「인용은 빼지 않는다」를 덧붙여도 같음, 기대 출처 122 → 117/124).

**원인 메시지가 화면에 내려오지 않는 것은 의도된 설계다**(정보 노출 방지). 대신 **막히면 서버 로그를
먼저 본다**는 것을 전제로 깔고 진행해야 한다. 로그를 안 보면 넷을 구분할 방법이 없다.

```bash
docker compose logs app | grep -iE "openai|vector|관리자"                      # 로컬
cd ~/deploy && sudo docker compose logs app | grep -iE "openai|vector|관리자"   # 운영 서버(ubuntu 는 docker 그룹이 아니다)
```

### 3-2. 검색 호출 정책 — 유도하되 강제하지 않는다

`tool_choice` 를 보내지 않는다. 기본값 `auto` 이므로 **file_search 호출 여부는 모델이 정한다.**
대신 검색 도구가 붙는 턴에 `instructions` 로 「사내 규정·절차처럼 조직마다 다른 내용은 반드시 검색
결과에 근거하고, 못 찾았으면 못 찾았다고 먼저 밝히라」고 지시한다(#39).

강제하지 않는 이유는 비용과 지연이다 — `tool_choice` 로 file_search 를 강제하면 단순 인사말에도
검색이 붙어 턴당 비용이 늘고 응답이 느려진다. **대가는 편차다.** 지시를 넣어도 모델이 검색을
건너뛰는 턴이 남을 수 있고, 그때 화면은 「자료 없음」이 된다 — 3-1 표의 「모델이 검색을 건너뜀」 행이 이것이다.

**인용 부착률이 낮게 나오면 그때 `tool_choice` 강제로 옮긴다.** 지시가 실려 나가는지는 `OpenAiRealInstructionsTest` 가
잠그므로, 낮다면 원인은 모델 쪽이다. 반대 방향(못 찾았는데 인용이 붙음, #181)도 함께 잰다 — 그래서 지시에
「근거를 찾지 못했으면 인용을 하나도 달지 않는다」가 있다. 현재 모델 실측(질문마다 새 대화) :

| `gpt-6-sol` (2026-10-15, #277) | **5/5** | **5/5** |

## 4. 비용이 발생하는 지점

투입 전에 알고 있어야 하는 과금 요소다. 단가는 변동하므로 OpenAI 가격표로 확인한다.

| 항목 | 과금 방식 | 비고 |
|------|-----------|------|
| 벡터 저장 | 1GB 무료, 초과분 일 단위 | **원본 파일 크기가 아니라** 파싱된 청크 + 임베딩 합계 기준이다. 텍스트 위주 문서는 기본 청킹(800토큰/400오버랩)에서 원본보다 커진다 |
| 검색 툴 호출 | 호출 건수 | 대화 턴마다 1회 붙는다 |
| 토큰 | 입력·출력 | 검색된 청크가 입력에 실려 들어간다 |
| 이미지 | 입력 토큰 | 첨부 이미지를 base64로 인라인한다. 과거 턴은 재전송하지 않는다 |

**계획 단계에서 먼저 잴 것** : 대표 문서 몇 건을 올려 Vector Store의 실측 크기와 원본 크기의 비율을
확인한다. 이 배율 하나가 월 비용을 한 자릿수 배 가른다. 추정으로 계산하지 않는다.

토큰 사용량은 `messages.input_tokens` · `output_tokens` 에 남는다(FEAT-OPS-001). 조회 SQL 과 주의점은 `docs/01_specs/erd.md` 6절.

## 5. 문서를 넣는 경로

**제품 안에 있다**(FEAT-ADMIN-002). `POST /api/admin/documents` 로 올리면 백엔드가 OpenAI Files 에
업로드하고 공용 Vector Store 에 연결한 뒤 `rag_documents` 에 기록한다 — 누가 언제 올렸는지가 저장소에 남는다.

**문서 관리 화면은 `/admin/documents`** 다. 마이페이지 → 문서 관리로 들어간다. API 를 직접 불러도 된다.

| 필요한 것 | 방법 |
|-----------|------|
| 관리자 계정 | `ADMIN_EMAILS` 에 이메일을 넣고 기동. 계정이 있으면 그 자리에서 승격되고, **없으면 계정째로 만들어지며 임시 비밀번호가 기동 로그에 한 번 찍힌다** |
| 업로드 | `POST /api/admin/documents` (multipart, 필드명 `file`). PDF · TXT · MD · DOCX, 최대 25MB |
| 상태 확인 | `GET /api/admin/documents` — `status` 가 `completed` 여야 검색에 잡힘 |
| 내리기 | `DELETE /api/admin/documents/{id}` |
| 스토어와 맞추기 | `POST /api/admin/documents/sync` — 화면의 「스토어와 동기화」 버튼(#193) |

**2-3(문서 1건)과 2-7(전량)을 이 경로로 한다 — 두 경로를 섞지 말 것.** 목록 조회(`AdminDocumentService.list()`)는
`rag_documents` 만 읽으므로, 대시보드로 올린 파일은 검색에는 잡히는데 관리 화면에서 보이지도 지워지지도 않고
에러도 나지 않는다. 2-1 에서 스토어를 비워 만들라고 한 이유가 이것이다.

**어긋났으면 「스토어와 동기화」로 메운다**(#193). 대시보드로 올린 파일, 또는 **다른 서버 DB 를 거쳐 올린 파일**
(로컬 개발 DB 로 올리고 운영 DB 는 새로 만든 경우)이 대상이다. 스토어의
파일 중 살아 있는 행이 없는 것만 행으로 넣고, 「올린 사람」은 동기화한 관리자로 남는다. 여러 번 눌러도 결과가 같다.
그래도 기록(누가 올렸나)이 남는 경로는 업로드뿐이므로 **새 문서는 여전히 관리 화면으로 올린다.**

**동기화는 파일이 지워진 스토어 연결도 정리한다**(#271) — 목록에 보이지 않는 고아 연결이 끊긴다(서버 로그 「파일이 없는 스토어 연결 n건을 정리함」).

### 5-1. 그림이 있는 문서 넣기 (FEAT-CHAT-004)

Vector Store 는 텍스트만 색인하므로 **그림은 따로 옮겨야 한다.** 원본 PDF 를 그대로 올리면 그림은 버려진다.

1. 전처리 — `python scripts/doc-figures/preprocess.py <원본 PDF> <출력 폴더> --prefix tm`
   (PyMuPDF 필요). 출력 폴더에 `<원본 이름>.md` · `figures/<key>.png` · `figures/manifest.json` 이 나온다
2. Markdown 을 위 경로(관리 화면 업로드)로 올린다. **같은 문서의 이전 버전은 먼저 지운다** — 둘 다 남으면
   표식 없는 옛 청크가 검색에 섞여 그림이 덜 나온다
3. `figures/*.png` 를 서버의 배포 디렉터리 `doc-figures/` 에 복사한다(compose 가 `/data/doc-figures` 로 읽기 전용 마운트).
   **저장소에 커밋하지 않는다** — 저장소가 공개다
4. 확인 — 매니페스트에서 키 하나를 골라 로그인 토큰으로 `GET /api/doc-figures/<key>` 가 200 인지 본다.
   404 면 파일 위치(`<루트>/<key>.png`)와 `DOC_FIGURES_DIR` 를 본다

**키는 쪽 번호와 쪽 안 순번으로 정해진다.** 원본이 바뀌어 쪽이 밀리면 같은 키가 다른 그림을 가리키게 되어,
지난 대화에 남은 표식이 엉뚱한 그림을 보인다. 원본을 바꿀 때는 `--prefix` 를 새로 정한다(예 : `tm2`).

### 5-2. 클레임 자료 넣기 — 개인정보를 지우고 올린다 (#266)

필드 클레임 엑셀은 반출승인이 없는 자료다. **스토어에 들어간 글은 답변과 출처 스니펫으로 누구에게나 다시 나온다** —
2026-10-15 QA 에서 연락처를 물으니 봇이 증상 본문에 적혀 있던 휴대폰 번호를 그대로 답했다.

1. 마스킹 목록을 자료 폴더에 둔다(**저장소 밖** — 저장소가 공개라 목록 자체가 유출이다). 한 줄에 하나 :
   `person <이름>` → `담당자-NN`, `partner <상호>` → `협력사-NN`. 같은 대상은 늘 같은 가명이다(등장 순 번호)
2. 전처리 — `python scripts/claims/preprocess.py <원본.xlsx> <출력.md> --mask-terms <목록 파일>`(openpyxl 필요).
   고객사 업체명(`업체명` 열)은 목록 없이 `고객사-NNN` 으로, 전화번호는 `[연락처 삭제]` 로 바뀐다.
   산출물은 **상세의 모든 줄 앞에 `[클레임 N]`** 을 붙이고 클레임마다 결론 요약 한 줄(서비스번호 · S/N · 기종 · 호기정보 · 불량유형 · 분석내용 · 불량원인 · 최종원인)을 머리 바로 밑에 두며(#267 · #468 — 조각이 상세 중간에서 끊겨도 서비스번호 · 호기로 찾은 조각에 이 값들이 함께 오게) 상세 줄에는 요약에 없는 필드만 남기고(#467 — 같은 값이 두 번 들어가면 키워드 점수가 부풀어 매뉴얼 조각이 검색에서 밀렸다) 머리에 전수 집계 표를 둔다(표 목록은 스크립트가 쓰는 `## 전체 요약 (집계)` 절이 정본) —
   기본 청킹은 클레임 경계를 모르므로 조각이 클레임 중간에서 시작해도 줄마다 출처가 남아야 하고,
   212건 전부는 한 번의 검색에 들어오지 않으므로 「몇 건」은 미리 세어 둔 표로만 답할 수 있다.
   몇 건짜리 항목은 표에 클레임 번호까지 적는다(#521 — 번호 없이 「3건」만 있으면 세 건을 상세 절에서 하나씩 검색으로 모으다 한 건을 빠뜨렸다).
   상세 끝 한 줄에만 있는 값도 표로 올린다(#531 — S/W 버전은 「21.3」 같은 짧은 값이라 그 줄이 든 조각이 검색에 아예 안 걸렸다).
   출하일 · 고장일 · 입고일자는 연도마다 반기 · 분기 · 월 합계까지 센다(#532 — 표에 없는 「2023년 1월 출하」 건수를 상세 절에서 세다 일부만 세고 틀린 수를 단정했다)
3. **exit 1 이면 올리지 않는다.** 마스킹 뒤 전화번호 패턴이나 「한글 이름 + 직함(님 · 부장 · 책임 …)」이 남았다는 뜻이고,
   이때는 산출물 파일을 아예 쓰지 않는다. 사람이면 목록에 더하고, 사람이 아니면 스크립트의 `NOT_A_NAME` 에 더한 뒤 다시 돌린다
4. 관리 화면으로 올리고, 옛 문서는 **올린 뒤에** 지운다(같은 문서 둘이 잠깐 겹치는 쪽이 비는 쪽보다 낫다).
   다른 서버 DB 는 옛 행 삭제 → 「스토어와 동기화」로 맞춘다(5절)

검사는 목록에 없는 이름을 **직함이 붙은 경우에만** 잡는다. 직함 없이 이름만 적힌 서술은 못 잡으므로, 새 원본이 들어오면
산출물을 한 번은 사람 눈으로 훑는다.

## 6. 되돌리기

**운영은 직전 백엔드 이미지로 되돌린다.** 운영 compose 는 `prod` 프로필을 켜고 `AppModeGuard` 가 prod + mock 기동을
거부하므로(#305) `APP_MODE=mock` 으로 바꾸면 백엔드가 아예 뜨지 않는다. 되돌릴 이미지(`:previous` · 손으로 남긴 `prev-<sha>`)를
남기는 규칙은 [backend.md](../02_architecture/backend.md) 「배포」에 있다.

`APP_MODE=mock` 은 **로컬 전용** 대피로다. 목업은 실 키 없이 전 경로가 동작하므로 원인을 찾을 시간을 벌 수 있다.
compose 로 띄우는 법은 [backend.md](../02_architecture/backend.md) 「실행 모드」에 있다 — 가드를 일부러 끄는 것이라 운영에서 쓰지 않는다.
