```bash
  -H "Authorization: Bearer $OPENAI_API_KEY"
```

## 0. 지금 상태를 정확히 적는다

`backend/src/main/java/com/ragchatbot/openai/OpenAiRealService.java` 는 **컴파일과 구조만 검증된 상태**다.
클래스 주석이 스스로 밝히고 있듯 실 응답과 대조한 적이 없다. 따라서 이 문서는 "설정만 넣으면 된다"가 아니라
**"설정을 넣은 뒤 무엇이 어긋날 수 있는지"** 를 함께 적는다.

검증되지 않은 가정은 3절에 전부 나열한다. 하나라도 어긋나면 증상이 다르게 나타나므로, 원인을 찾는 데
쓰는 시간을 줄이려면 그 목록을 먼저 훑는 편이 빠르다.

## 1. 준비물

| 준비물 | 환경변수 | 없으면 생기는 일 |
|--------|----------|------------------|
| **PostgreSQL** | `DB_URL` · `DB_USERNAME` · `DB_PASSWORD` | **기동 실패.** `application.yml:10` 의 `${DB_URL:}` 이 비면 DataSource 가 드라이버를 정하지 못한다. URL 은 `jdbc:postgresql://…` 형식이어야 하며, 관리형 DB 가 주는 `postgres://user:pass@host/db` 를 그대로 넣으면 뜨지 않는다. **compose 로 띄우면 이 셋은 compose 가 덮어쓰므로 신경 쓰지 않아도 된다** |
| **JWT 서명 시크릿** | `JWT_SECRET` | **기동 실패**(`JwtService.java:31-33`). 32바이트 이상 임의 문자열 — `openssl rand -base64 48` |
| OpenAI API 키 | `OPENAI_API_KEY` | `APP_MODE=live` 기동 즉시 실패(fail-fast). per-request 401로 흐르지 않는다 |
| 공용 Vector Store ID | `OPENAI_VECTOR_STORE_ID` | 기동·응답은 되지만 `file_search` 툴을 아예 붙이지 않아 **출처가 항상 0건**이 된다 |
| 모델 이름 | `OPENAI_MODEL` | 미지정 시 `gpt-4o`. 비전 입력을 쓰므로 **이미지 지원 모델이어야 한다** |
| 실행 모드 | `APP_MODE=live` | 미설정이면 `AppModeGuard`가 기동을 막는다(의도된 설계) |
| **계정 허용 도메인** | `ALLOWED_EMAIL_DOMAINS` | **기동 즉시 실패**(FEAT-AUTH-001). 비면 관리자의 오타 한 번으로 사외 주소에 계정이 열리므로, 조용히 열리지 않도록 일부러 막는다 |
| 관리자 이메일 명단 | `ADMIN_EMAILS` | 관리자가 0명이 되어 **문서를 등록할 사람이 없다.** 기동은 정상이라 5절 단계에서야 드러난다 |

전량은 `backend/.env.example` 에 이름만 적혀 있다. 값은 저장소에 넣지 않는다.

**기동을 막는 것은 여섯이다** — `APP_MODE` · `OPENAI_API_KEY` · `ALLOWED_EMAIL_DOMAINS` · `JWT_SECRET` ·
`DB_URL`(+ `DB_USERNAME` · `DB_PASSWORD`). 하나라도 비면 컨텍스트가 뜨지 않으므로 **기동에 성공했다는
사실 자체가 이 여섯이 들어갔다는 근거**가 된다.

나머지는 기동은 되고 **나중에 증상으로 드러나므로** 더 찾기 어렵다 :

| 빠뜨린 것 | 드러나는 시점 | 증상 |
|-----------|--------------|------|
| `OPENAI_VECTOR_STORE_ID` | 2-3 | 업로드가 400 `Vector Store 가 설정되지 않아 업로드할 수 없음` 으로 거부된다. 업로드를 건너뛰어도 `file_search` 툴이 아예 안 붙어 **출처가 늘 0건**이 된다 |
| `ADMIN_EMAILS` | 2-3 | 관리자가 0명이라 **로그인할 계정 자체가 없다.** 스스로 가입하는 경로가 없어 되돌릴 방법이 재기동뿐이다 |
| `OPENAI_MODEL` (비전 미지원으로 바꾼 경우) | 2-6 | 이미지 첨부만 답변이 어긋난다 |

**`ADMIN_EMAILS` 의 주소는 `ALLOWED_EMAIL_DOMAINS` 밖이어도 된다.** 도메인 검사를 면제받으므로
관리자 이메일이 사내 도메인이 아니어도 부트스트랩이 막히지 않는다.

### 1-1. 값을 어떻게 넣는가

**`backend/.env` 는 저절로 읽히지 않는다.** 저장소에 dotenv 로더가 없고(`backend/pom.xml`)
`spring.config.import` 도 걸려 있지 않다. 그 파일을 실제로 소비하는 곳은 `docker-compose.yml` 의
`env_file` **한 곳뿐**이다. 이것을 모르면 `.env` 를 정성껏 채우고도 `APP_MODE 미설정` 으로 기동에 실패하고,
방금 값을 적어 넣은 사람에게 그 메시지는 원인을 가리키지 않는다.

| 띄우는 방법 | 값이 들어가는 경로 |
|-------------|--------------------|
| **`docker compose` (권장)** | `backend/.env` 를 `env_file` 로 읽는다. DB 접속 셋은 compose 가 덮어쓰므로 루트 `.env` 의 `POSTGRES_PASSWORD` 하나만 맞추면 된다. 절차는 [`backend.md` 「배포」](../02_architecture/backend.md) |
| `./mvnw spring-boot:run` | **`.env` 를 읽지 않는다.** 셸에 직접 넣어야 한다 — `export $(grep -v '^#' backend/.env \| xargs)` 또는 변수를 하나씩 `export` |

권장은 compose 다. DB 컨테이너가 함께 뜨므로 위 표의 `DB_*` 를 따로 준비할 필요가 없고,
실 배포와 같은 경로를 밟게 되어 "로컬에서는 됐는데" 가 줄어든다.

## 2. 투입 절차

각 단계는 **다음 단계로 넘어가기 전에 확인할 것**을 함께 적는다. 확인 없이 다음으로 넘어가면
실패했을 때 어느 단계가 원인인지 분리되지 않는다.

> **순서를 지켜야 하는 이유** — 문서를 넣는 유일한 경로가 제품 화면인데(5절), 그 경로는
> `OPENAI_VECTOR_STORE_ID` 가 이미 주입돼 **기동한 뒤에만** 열린다(`AdminDocumentService.java:85-88`).
> 그래서 스토어를 만드는 것과 문서를 넣는 것이 붙어 있지 않고, 사이에 기동이 들어간다.
> 대시보드에서 문서까지 올려 두면 순서는 짧아지지만 관리 화면에서 보이지도 지워지지도 않는 상태가 된다.

### 2-1. 빈 Vector Store 를 만들고 ID 만 챙긴다

**문서는 넣지 않는다.** 스토어만 만들고 `vs_` 로 시작하는 ID 를 복사한다.

- 확인 : 위쪽 「밖에서 먼저 만들어 와야 하는 것 둘」 의 curl 이 200 을 돌려준다. 401 이면 키가,
  403 이면 권한이 문제다.

### 2-2. 환경변수를 넣고 백엔드를 `APP_MODE=live` 로 띄운다

1-1 의 방법으로 값을 주입한다. `OPENAI_VECTOR_STORE_ID` 에 2-1 의 ID 를 넣는다.

- 확인 : 기동이 성공한다. **1절의 여섯 중 하나라도 비면 여기서 즉시 실패**하므로, 기동됐다는 것
  자체가 여섯이 다 들어갔다는 근거다.
- 확인 : 기동 로그의 `관리자 명단 동기화 : 명단 N건 · 생성 N건 …` 줄을 본다. 명단 건수가 0이면
  `ADMIN_EMAILS` 를 빠뜨린 것이고, 그대로 두면 다음 단계에서 **로그인할 계정이 없다.**
- 확인 : 계정이 새로 만들어졌다면 로그에 `관리자 계정 발급 : … 임시 비밀번호 XXXX-XXXX-XXXX` 가
  **한 번만** 찍힌다. 재발급 경로가 없으므로 그 자리에서 옮겨 적는다.

**`vs_` ID 가 틀려도 기동은 성공한다.** 형식·실재를 검사하는 코드가 없어(`OpenAiRealService.java:338-340`
는 공백 여부만 본다) 오타는 2-3 이나 2-4 에서야 드러난다. 증상과 대처는 3-1 에 있다.

### 2-3. 관리자로 로그인해 문서 1건만 올린다

처음부터 전량을 올리지 않는다. **문서 1건**이면 3절의 가정이 전부 드러난다.
경로는 `/admin` 화면 또는 `POST /api/admin/documents` — 둘 다 5절의 같은 경로다.
**OpenAI 대시보드로 올리지 않는다**(이유는 5절).

- 확인 : 응답이 201 이고 `status` 가 `in_progress` 다.
- 확인 : `GET /api/admin/documents` 를 다시 불러 `status` 가 `completed` 로 바뀐다.
  `in_progress` 로 멈춰 있으면 파싱 단계에서 막힌 것이라 아래 단계가 전부 무의미하다.

### 2-4. 2-3에서 올린 문서의 내용을 묻는다

- 확인 ① : 답변 토큰이 **흘러서** 온다(한 번에 뭉쳐 오지 않는다). 뭉쳐 오면 스트리밍이 아니라
  버퍼링된 것이므로 `RestClient` 응답 처리를 봐야 한다.
- 확인 ② : 진행 단계에 **「참조 문서 검색 중」** 이 뜬다. 안 뜨면 `file_search` 호출 이벤트가
  도착하지 않은 것이다(3절 가정 A).
- 확인 ③ : 답변 하단에 **출처 각주가 뜬다**. 각주가 없고 「자료 없음」 배너가 뜨면 인용 추출이
  실패한 것이다(3절 가정 B·C).

### 2-5. 자료에 없는 것을 묻는다

- 확인 : 「자료 없음 - 관련 자료를 찾지 못해 추론으로 답변함」 배너가 뜬다. 2-4와 2-5가 **모두**
  기대대로 나와야 무자료 판정이 동작하는 것이다. 한쪽만 보면 "항상 0건"과 구분되지 않는다.

### 2-6. 이미지를 첨부해 묻는다

- 확인 : 이미지 내용을 반영한 답변이 온다. `OPENAI_MODEL` 을 비전 미지원 모델로 바꿨다면 여기서 드러난다.

### 2-7. 전량 업로드

2-1~2-6이 전부 통과한 뒤에 문서를 전량 올린다. 경로는 2-3과 같다. 이 시점부터는 저장 용량 과금이 시작된다.

## 3. 실 응답과 대조해야 하는 가정

아래는 **문서만 보고 작성돼 실물로 확인된 적이 없는** 값들이다. 2-4에서 기대와 다른 결과가 나오면
여기부터 본다.

| ID | 가정 | 어긋나면 나타나는 증상 |
|----|------|------------------------|
| A | 검색 시작 이벤트 이름이 `response.file_search_call.in_progress` 또는 `response.file_search_call.searching` | 「참조 문서 검색 중」 단계가 화면에 뜨지 않는다. 답변은 정상 |
| B | 완료 이벤트 이름이 `response.completed` | **스트림이 완료 없이 끝났다**는 오류로 끝난다. 조용히 무자료로 넘어가지 않도록 일부러 던지게 해 둔 경로다 |
| C | 인용 annotation의 타입이 `file_citation` 이고 파일명 필드가 `filename` | 답변은 정상인데 출처가 늘 0건이라 **모든 답변에 「자료 없음」 배너**가 붙는다 |
| D | 검색 결과 본문이 `file_search_call` 항목의 `results[].text` 에 실린다 | 출처 각주는 뜨는데 스니펫이 빈칸이다 |
| E | `include: ["file_search_call.results"]` 로 결과 본문을 받을 수 있다 | D와 같은 증상 |

가정 C는 특히 **오진하기 쉽다.** "자료 없음"은 정상 동작으로도 나오는 표시라, 스토어에 문서가 있는데도
0건이면 검색이 안 된 것인지 인용 추출이 깨진 것인지 화면만 봐서는 구분되지 않는다. 2-4에서
**스토어에 확실히 있는 내용**을 물어 구분한다.

### 3-1. 증상에서 원인으로 — 어디부터 보는가

같은 화면이 여러 원인에서 나온다. 특히 **「자료 없음」 하나에 원인이 넷** 몰려 있어, 화면만 보고는
갈라지지 않는다. 아래는 증상에서 거슬러 올라가는 순서다.

| 증상 | 먼저 볼 것 | 갈라내는 방법 |
|------|-----------|--------------|
| 전 답변에 「자료 없음」 | `OPENAI_VECTOR_STORE_ID` 가 비었는지 | 비면 `file_search` 툴이 아예 안 붙는다. 2-3 업로드가 400 으로 거부됐다면 이쪽이 확실하다 |
| 〃 | `vs_` ID 오타 | 업로드가 500 으로 실패한다. 서버 로그에 `openai … 400`·`404` 가 남는다 |
| 〃 | 인용 추출(가정 C) | 업로드는 `completed` 인데 출처만 0건이면 이쪽 |
| 〃 | 모델이 검색을 건너뜀 | 위 셋이 아니면 남는 것은 이것이다. `instructions` 로 유도하되 `tool_choice` 로 강제하지는 않는다(아래 3-2) |
| 채팅이 `"응답 생성 중 오류"` 로 끝남 | 서버 로그 | OpenAI 응답 본문은 화면에 내려가지 않는다. 단서는 `openai responses api error <코드>: {...}` 한 줄뿐이다 |
| 업로드가 `"처리 중 오류가 발생했습니다 (오류 번호: …)"` | 서버 로그 | 같은 이유로 원인이 화면에 없다. 오류 번호로 로그를 찾는다 |

**원인 메시지가 화면에 내려오지 않는 것은 의도된 설계다**(정보 노출 방지). 대신 **막히면 서버 로그를
먼저 본다**는 것을 전제로 깔고 진행해야 한다. 로그를 안 보면 넷을 구분할 방법이 없다.

```bash
docker compose logs app | grep -iE "openai|vector|관리자"
```

### 3-2. 검색 호출 정책 — 유도하되 강제하지 않는다

`tool_choice` 를 보내지 않는다. 기본값 `auto` 이므로 **file_search 호출 여부는 모델이 정한다.**
대신 검색 도구가 붙는 턴에 `instructions` 로 「사내 규정·절차처럼 조직마다 다른 내용은 반드시 검색
결과에 근거하고, 못 찾았으면 못 찾았다고 먼저 밝히라」고 지시한다(#39).

강제하지 않는 이유는 비용과 지연이다 — `tool_choice` 로 file_search 를 강제하면 단순 인사말에도
검색이 붙어 턴당 비용이 늘고 응답이 느려진다. **대가는 편차다.** 지시를 넣어도 모델이 검색을
건너뛰는 턴이 남을 수 있고, 그때 화면은 「자료 없음」이 된다 — 3-1 표의 「모델이 검색을 건너뜀」 행이 이것이다.

**실 연동에서 부착률을 재 본 뒤 다시 판단할 자리다.** 스토어에 확실히 있는 내용을 여러 번 물어
인용이 붙는 비율을 보고, 낮으면 `tool_choice` 강제로 옮긴다. 지시가 실제로 실려 나가는지는
`OpenAiRealInstructionsTest` 가 잠그고 있으므로, 부착률이 낮다면 원인은 보내는 쪽이 아니라 모델 쪽이다.


## 4. 비용이 발생하는 지점

투입 전에 알고 있어야 하는 과금 요소다. 수치는 2026-08 기준이며 변동한다.

| 항목 | 과금 방식 | 비고 |
|------|-----------|------|
| 벡터 저장 | 1GB 무료, 초과분 일 단위 | **원본 파일 크기가 아니라** 파싱된 청크 + 임베딩 합계 기준이다. 텍스트 위주 문서는 기본 청킹(800토큰/400오버랩)에서 원본보다 커진다 |
| 검색 툴 호출 | 호출 건수 | 대화 턴마다 1회 붙는다 |
| 토큰 | 입력·출력 | 검색된 청크가 입력에 실려 들어간다 |
| 이미지 | 입력 토큰 | 첨부 이미지를 base64로 인라인한다. 과거 턴은 재전송하지 않는다 |

**계획 단계에서 먼저 잴 것** : 대표 문서 몇 건을 올려 Vector Store의 실측 크기와 원본 크기의 비율을
확인한다. 이 배율 하나가 월 비용을 한 자릿수 배 가른다. 추정으로 계산하지 않는다.

토큰 사용량은 이제 `messages.input_tokens` · `output_tokens` 에 남는다(FEAT-OPS-001).
**집계 화면은 없으므로** 조회는 DB 직접 질의뿐이며, SQL 예시는 `docs/01_specs/erd.md` 6절에 있다.
`where input_tokens is not null` 조건을 빼면 목업·중단 턴이 0으로 섞여 턴당 평균이 실제보다 낮게 나온다.

## 5. 문서를 넣는 경로

**제품 안에 있다**(FEAT-ADMIN-002). `POST /api/admin/documents` 로 올리면 백엔드가 OpenAI Files 에
업로드하고 공용 Vector Store 에 연결한 뒤 `rag_documents` 에 기록한다 — 누가 언제 올렸는지가 저장소에 남는다.

**관리자 화면은 `/admin`** 이다. 마이페이지 → 문서 관리로 들어간다. API 를 직접 불러도 된다.

| 필요한 것 | 방법 |
|-----------|------|
| 관리자 계정 | `ADMIN_EMAILS` 에 이메일을 넣고 기동. 계정이 있으면 그 자리에서 승격되고, **없으면 계정째로 만들어지며 임시 비밀번호가 기동 로그에 한 번 찍힌다** — 이 주소는 `ALLOWED_EMAIL_DOMAINS` 밖이어도 만들어진다 |
| 업로드 | `POST /api/admin/documents` (multipart, 필드명 `file`). PDF · TXT · MD · DOCX, 최대 50MB |
| 상태 확인 | `GET /api/admin/documents` — `status` 가 `completed` 여야 검색에 잡힘 |
| 내리기 | `DELETE /api/admin/documents/{id}` |

**2-3(문서 1건)과 2-7(전량)을 이 경로로 하면 된다.** OpenAI 대시보드를 거치지 않아도 되고, 그렇게 해야
기록이 남는다. 대시보드에서 직접 올린 문서는 검색에는 잡히지만 `rag_documents` 에 행이 없어
관리 화면에서 보이지도 지워지지도 않는다 — **두 경로를 섞지 말 것.**

목록 조회(`AdminDocumentService.list()`)가 `rag_documents` 만 읽고 **OpenAI 에 「이 스토어에 무슨 파일이
있냐」고 묻지 않기 때문**이다. 대시보드로 올린 파일은 채팅 검색에는 잡히지만 관리 화면에서는 처음부터
없었던 것처럼 보이고, 지울 방법도 화면에는 없다. **에러가 나지 않아 고장으로 보이지도 않는다** —
2-1 에서 스토어를 비워 만들라고 한 이유가 이것이다.

채팅 첨부(`backend/src/main/java/com/ragchatbot/service/FileService.java`)는 여전히 이미지만 받는다.
그쪽은 비전 입력용이고 이쪽은 색인용이라 허용 목록이 반대다.
