## 1. 프로젝트 개요

### 1.1 배경 및 목적

사내 규정·정책 문서를 근거로 답하는 챗봇이다. 일반 LLM 챗봇과 다른 점은 **답변의 출처를 항상 밝히고,
근거 자료를 찾지 못했으면 그 사실을 먼저 알린 뒤 추론한다**는 것이다.

해결하려는 문제는 "그럴듯하지만 근거 없는 답변"이다. 사내 규정처럼 틀리면 실제 손해가 생기는 영역에서는
답변의 정확도만큼이나 **어디까지가 자료에 근거한 것인지 구분되는가**가 중요하다.

### 1.2 범위

| 포함 | 제외 |
|------|------|
| 자체 이메일/비밀번호 인증 + **관리자 발급** + 도메인 제한 | SSO · 소셜 로그인 · 이메일 인증 · 셀프 가입 |
| 대화별 스트리밍 답변 + 출처 각주 | 답변 평가·피드백 수집 |
| 이미지 첨부(비전 입력) | 문서 첨부를 대화에서 근거로 쓰기 |
| 공용 Vector Store 기반 문서 검색 | 대화별 개인 문서 스토어 |
| 관리자의 RAG 문서 관리 | 문서 버전 관리 · 승인 워크플로 |
| 사용량 기록 | 사용량 집계 화면 · 과금 |

### 1.3 용어 정의

| 용어 | 정의 |
|------|------|
| 무자료 | 답변에 인용된 출처가 0건인 상태. 추론으로만 답한 것임을 화면에 밝힌다 |
| 공용 Vector Store | 전 사용자가 공유하는 단일 검색 대상. 대화별 스토어를 두지 않는다 |
| 중단 | 사용자가 답변 생성을 끊은 것. **실패가 아니다** — 받은 데까지 정상 저장한다 |
| 타임아웃 | 서버가 SSE 스트림을 수명 상한으로 닫은 것. 중단과 **저장 모양이 겹치므로** `timed_out` 으로 구분한다 |
| 진행 단계 | 답변 생성 중 화면에 뜨는 문구(분석 · 검색 · 참조 문서 확인 · 작성). 실제로 지난 경계에서만 올린다 |
| 목업 모드 | `APP_MODE=mock`. 실 API 키 없이 전 경로가 동작한다 |

## 4. 기능 요구사항

카테고리는 `AUTH`(인증) · `CHAT`(대화·첨부) · `RAG`(검색·출처) · `ADMIN`(관리) · `OPS`(운영) 다섯이다.
**모든 후속 문서가 이 카테고리를 그대로 쓴다.**

### AUTH — 인증

| ID | 요구사항 | 우선순위 | 상태 |
|----|---------|---------|------|
| REQ-AUTH-001 | 관리자가 발급한 계정으로 로그인할 수 있어야 한다 | `Must` | 구현됨 |
| REQ-AUTH-002 | 비밀번호는 평문으로 저장되지 않아야 한다 | `Must` | 구현됨 (BCrypt) |
| REQ-AUTH-003 | 비밀번호를 바꾸면 이전에 발급된 **세션**이 전부 끊겨야 한다 | `Must` | 구현됨. **첨부 서빙 토큰(`aud=file`)은 제외** — `docs/02_architecture/overview.md` 「알려진 제약」 |
| REQ-AUTH-004 | 로그인 시도를 무제한 반복할 수 없어야 한다 | `Should` | 구현됨 (분당 상한) |
| REQ-AUTH-005 | 업무 중에 세션이 끊겨 작성하던 내용이 사라지지 않아야 한다 | `Should` | 구현됨 (슬라이딩 재발급) |
| REQ-AUTH-006 | 비밀번호를 잊은 사용자가 복구할 경로가 있어야 한다 | `Should` | 구현됨 (관리자 초기화) |
| REQ-AUTH-007 | **사내 구성원이 아닌 사람이 계정을 만들 수 없어야 한다** | `Must` | 구현됨 |

### CHAT — 대화·첨부

| ID | 요구사항 | 우선순위 | 상태 |
|----|---------|---------|------|
| REQ-CHAT-001 | 사용자는 **보내기 전에** 첨부한 이미지가 무엇인지 확인할 수 있어야 한다 | `Must` | 구현됨 |
| REQ-CHAT-002 | 사용자는 첨부 이미지를 **원본 크기로** 다시 볼 수 있어야 한다 | `Must` | 구현됨 |
| REQ-CHAT-003 | 첨부 상태(업로드 중·완료·실패)가 화면에 드러나야 한다 | `Must` | 구현됨 |
| REQ-CHAT-004 | 첨부 경로가 파일 선택기 하나로 좁혀지지 않아야 한다 | `Should` | 구현됨 |
| REQ-CHAT-005 | 답변이 생성되는 동안 진행 상황이 보여야 한다 | `Should` | 구현됨 |
| REQ-CHAT-006 | 사용자가 답변 생성을 중단해도 받은 내용이 남아야 한다 | `Must` | 구현됨 |
| REQ-CHAT-007 | 이전 대화 맥락이 답변에 반영되어야 한다 | `Should` | 구현됨 (토큰 예산 내) |

### RAG — 검색·출처

| ID | 요구사항 | 우선순위 | 상태 |
|----|---------|---------|------|
| REQ-RAG-001 | 답변에 사용된 자료의 출처가 각주로 표시되어야 한다 | `Must` | 구현됨 |
| REQ-RAG-002 | 출처는 대화를 다시 열어도 남아 있어야 한다 | `Must` | 구현됨 (영속화) |
| REQ-RAG-003 | 근거 자료가 없으면 **그 사실을 밝힌 뒤** 답해야 한다 | `Must` | 구현됨 |
| REQ-RAG-004 | 참조한 적 없는 자료명을 화면에 만들어내지 않아야 한다 | `Must` | 구현됨 |
| REQ-RAG-005 | 실 연동이 실 응답과 대조되어야 한다 | `Must` | 검증됨 (2026-09-22 로컬 실응답 · `live-integration.md` 3절) |
| REQ-RAG-006 | 근거 문서에 답과 관련된 그림이 있으면 답변에 그 그림이 함께 보여야 한다 | `Should` | 구현됨 (FEAT-CHAT-004) |

### ADMIN — 관리

| ID | 요구사항 | 우선순위 | 상태 |
|----|---------|---------|------|
| REQ-ADMIN-001 | 사내 문서를 **제품 안에서** 공용 Vector Store에 올릴 수 있어야 한다 | `Must` | 구현됨 |
| REQ-ADMIN-002 | 누가 언제 어떤 문서를 올리고 지웠는지 저장소에 남아야 한다 | `Must` | 구현됨 |
| REQ-ADMIN-003 | 인덱싱 실패를 관리자가 알 수 있어야 한다 | `Must` | 구현됨 |
| REQ-ADMIN-004 | 문서를 관리할 수 있는 사람과 아닌 사람이 구분돼야 한다 | `Must` | 구현됨 |
| REQ-ADMIN-005 | 관리자가 더 쓰지 않는 계정을 그 사용자의 대화 · 첨부와 함께 지울 수 있어야 한다. 감사 기록(REQ-ADMIN-002)은 지워지지 않아야 한다 | `Should` | 예정(#513, FEAT-ADMIN-004) |

### OPS — 운영

| ID | 요구사항 | 우선순위 | 상태 |
|----|---------|---------|------|
| REQ-OPS-001 | 턴마다 실제로 쓴 토큰 수가 저장에 남아야 한다 | `Must` | 구현됨 |
| REQ-OPS-002 | 예상하지 못한 예외도 일관된 오류 형태로 나가고 서버에 흔적이 남아야 한다 | `Must` | 구현됨 |
| REQ-OPS-003 | 사용자별 요청량에 상한이 있어야 한다 | `Must` | 구현됨 |
| REQ-OPS-004 | 첨부 파일이 무한히 쌓이지 않아야 한다 | `Should` | 구현됨 (고아 회수) |

## 5. 비기능 요구사항

| 항목 | 요구사항 | 측정 기준 |
|------|---------|---------|
| 성능 | 답변 첫 토큰이 눈에 띄게 늦지 않아야 한다 | 스트리밍이 실제로 증분 수신되는지(뭉쳐 오지 않는지) |
| 성능 | 동시 스트림이 서버를 마비시키지 않아야 한다 | 상한 초과 시 큐에 쌓지 않고 429로 거절 |
| 보안 | 남의 대화·첨부에 접근할 수 없어야 한다 | 소유권 위반은 404로 은닉 |
| 보안 | API 키가 클라이언트에 노출되지 않아야 한다 | 모든 OpenAI 호출이 백엔드 뒤에만 존재 |
| 보안 | 업로드 파일이 확장자만 위조되어 통과하지 않아야 한다 | 매직바이트 검사 |
| 가용성 | 외부 API 키가 없어도 개발·시연이 가능해야 한다 | 목업 모드로 전 경로 동작 |
| 확장성 | 단일 인스턴스 전제다 | **한계로 명시** — 6절 제약 참고 |

## 6. 제약 조건

운영 · 플랫폼 제약(단일 인스턴스 · 첨부 로컬 디스크 · Spring Boot 4.1 트랙 · 소급 보정 없음 · 도메인 검사 시점)의 정본은
[overview](../02_architecture/overview.md) 「알려진 제약」, 스키마 쪽은 [erd.md](./erd.md) 「설계 원칙」이다. 여기에는 요구사항 수준의 것만 둔다.

- **RAG 검색·인용을 OpenAI 플랫폼에 위임** — 파싱·청킹·임베딩·인용 생성을 직접 하지 않는다.
  대가로 벡터 저장 용량에 비례하는 비용이 발생하고, 이관 시 인용 재구현이 가장 비싸다.
